# GIP-0001: Purpose and Guidelines

```
Title: Purpose and Guidelines
Author: BLOCH Founder <founder@blochlayer.com>
Status: Active

```

## What is a GIP?

GIP stands for **BLOCH Improvement Proposal**. A GIP is a design document providing information to the Bloch-SIS Protocol community, or describing a new feature for the protocol, its processes, or its environment. The GIP should provide a concise technical specification of the feature and a rationale.

The GIP author is responsible for building consensus within the community and documenting dissenting opinions.

This process is directly adapted from Bitcoin's BIP-1 and Python's PEP-1. Credit to the original authors.

## Why GIPs?

Bloch-SIS Protocol is a sovereign protocol with no central authority. GIPs provide the mechanism by which protocol changes are proposed, discussed, specified, and activated — without an on-chain vote, without a foundation, without automated deployment.

GIPs are not binding. A merged GIP does not compel any node operator to upgrade. Adoption is voluntary. Consensus changes activate only when supermajority hashrate signals support (BIP-9 style).

## GIP types

There are three kinds of GIP:

- **Standards Track**: describes any change that affects most or all Bloch-SIS Protocol implementations, such as a change to the network protocol, a change in block or transaction validity rules, or any change that affects interoperability.
- **Informational**: describes an Bloch-SIS Protocol design issue, or provides general guidelines or information to the community. An Informational GIP does not necessarily represent a community consensus or recommendation.
- **Process**: describes a process surrounding Bloch-SIS Protocol, or proposes a change to a process. This GIP-0001 is a Process GIP.

## GIP workflow

### 1. Pre-GIP (idea stage)

Discuss the idea in GitHub Issues or Discussions first. Many ideas do not need a GIP — a pull request to the reference implementation with good discussion may suffice.

A GIP is typically needed when:

- The change affects consensus rules
- The change affects block/transaction data formats
- The change is a significant protocol extension
- The change is controversial and benefits from formal specification

### 2. Draft

The champion (author) writes the GIP as a Pull Request to the `gips/` directory of the reference repository. The GIP number is assigned by the editor after a brief pre-review. PR title: `GIP-XXXX: Title`.

The GIP must follow the template structure (see `gips/TEMPLATE.md`). A GIP editor will review for structural completeness (not content).

When the Pull Request is opened with minimum structural quality, the GIP is marked as `Status: Draft` and merged into the `gips/` directory. **Merge of a Draft GIP does not imply endorsement — it only makes the proposal canonical.**

### 3. Proposed

After a Draft has accumulated substantial community discussion (typically in the GIP's tracking issue), and the author believes it is ready for formal review, they update the status to `Proposed`.

Proposed GIPs must include:

- Complete specification
- Reference implementation (or a clear path to one)
- Backward compatibility analysis
- Security considerations
- Test vectors

### 4. Active / Final

A Proposed GIP becomes `Active` when:

- For Standards Track affecting consensus: hashrate signaling reaches 95% for 2016 consecutive blocks (BIP-9 style)
- For Standards Track not affecting consensus (e.g., RPC additions): the reference implementation ships with it in a released version
- For Informational / Process GIPs: when maintainers merge a status change to Active

`Final` is used for Standards Track GIPs that have been activated and deployed. A `Final` GIP is immutable.

### 5. Rejected / Withdrawn

- **Rejected**: if the community reaches rough consensus that the GIP should not proceed. The GIP remains in the repository with its status updated.
- **Withdrawn**: if the author themselves decides to withdraw. Other authors may later propose similar ideas as new GIPs.

## GIP editors

GIP editors are responsible for:

- Assigning GIP numbers
- Checking structural quality on submission
- Updating status on valid requests
- Ensuring GIPs are discoverable

Editors do NOT approve or reject GIPs on content merit. They are a process role, not a gatekeeping role.

**Current editors**: listed in `gips/EDITORS.md`.

## GIP format

GIPs are plain Markdown files, named `GIP-XXXX.md`, stored in the `gips/` directory.

Each GIP MUST have a preamble block at the top with the following fields:

- `GIP`: integer, assigned by editor
- `Title`: short descriptive title
- `Author`: name and contact (email or @github handle)
- `Status`: one of Draft, Proposed, Active, Final, Rejected, Withdrawn
- `Type`: one of Standards Track, Informational, Process
- `Created`: ISO 8601 date (YYYY-MM-DD)
- `Replaces`: GIP number(s) this supersedes, if any (optional)
- `Superseded-By`: GIP number(s) that supersede this one, if any (optional)

Followed by these sections in order:

- **Abstract** — one paragraph summary
- **Motivation** — what problem this solves and why the solution fits
- **Specification** — exhaustive technical description; a competent engineer should be able to implement the GIP from this document alone
- **Rationale** — why these design choices; what alternatives were considered and rejected
- **Backward compatibility** — does this break existing behavior; how do nodes on old software experience this change
- **Security considerations** — what new attack surfaces does this create; how are they mitigated
- **Test vectors** — concrete input/output examples for implementers
- **Reference implementation** — link to PR or code in the reference Rust node

See `gips/TEMPLATE.md` for a concrete starter template.

## GIP numbering

- **GIP-0001**: this document (Purpose and Guidelines)
- **GIP-0002 to GIP-0009**: reserved for process GIPs
- **GIP-0010+**: assigned sequentially as Draft GIPs are merged

## Relationship to other proposals

Bloch-SIS Protocol adopts relevant Bitcoin BIPs and Ethereum EIPs when applicable. Instead of re-specifying, an Bloch-SIS Protocol GIP may reference the external document and specify only the adaptations needed.

Example: `GIP-0042: Adopt BIP-9 style versionbits signaling for soft fork activation` would reference BIP-9 directly.
