# GIP-0002: Network-bound transfer signatures and a signed commission cap for delegations

```
GIP: 0002
Title: Network-bound transfer signatures and a signed commission cap for delegations
Author: Postern Labs protocol team
Status: Draft
Type: Standards Track
Created: 2026-11-17
```

Activation follows the flag-day model that replaced GIP-0001's signalling
(see the note at the top of GIP-0001): named epoch constants compiled into
every node, armed by the owner in one release commit. **Nothing in this GIP is
armed.** All four constants it adds or uses ship as `u64::MAX`.

## Abstract

Two consensus changes from the wallet security review of November 2026, each
introduced through a dual-acceptance window.

- **WT-03.** A transfer (`Transfer`, tag `0x01`; `TransferV2`, tag `0x06`) is
  signed over a root that names no network. This GIP makes the signature
  cover the network's genesis-manifest digest. The node already carried that
  rule behind one disabled epoch; this GIP adds an earlier epoch from which
  the new root is accepted next to the old one, so signers can move before
  the old root is refused.
- **WT-04.** A funded delegation (`FundedDelegate`, tag `0x0E`) does not say
  what commission the delegator accepts. This GIP adds `FundedDelegateV2`
  (tag `0x1C`), whose signed intent carries `max_commission_bps`, and refuses
  it when the validator's commission is above that value in the block that
  would admit it.

## Motivation

### WT-03: transfers replay across networks

`spend_signing_root` is `SHA3-256(DS_SPEND ‖ inputs ‖ outputs ‖ tx_bytes ‖
tip)`. `DS_SPEND` is the same on every network built from this code, and the
preimage contains no chain identifier. Two networks that hold the same
outpoint under the same key therefore accept the same signed bytes. Networks
opened from one carryover snapshot share hundreds of thousands of such
outpoints, because allocation transaction ids are a function of the snapshot
alone. A transfer signed on a development network derived from mainnet state
can be submitted on mainnet by anyone who sees it.

The wallet currently proves that its RPC endpoint is mainnet before it signs.
That protects a careful user of that wallet. It does not protect a signature
once it exists, and it does nothing for other signers.

### WT-04: the commission can change under a signed delegation

A validator may raise its commission whenever no delegation targets it
(`ValidatorCommissionUpdate`, tag `0x11`). A delegator reads 5%, signs, and
broadcasts. Before the request is included the validator raises its
commission to 100%: the raise is valid, the request is then admitted, and from
that block the raise could no longer happen but already has. The delegator
earns nothing and can leave only through the cool-down (32 epochs) and the
withdrawal delay (2,048 epochs), about 23 days at 16 minutes per epoch. The
principal is not at risk; the rewards of that period are.

## Specification

Epochs are those of the block being judged (`CommittedState::epoch`), never a
clock. `u64::MAX` means "never", including at epoch `u64::MAX`.

### 1. Dual-acceptance gate

```
DualAcceptanceGate { accept_epoch, enforce_epoch }
accepted(e) = (accept_epoch != MAX and e >= accept_epoch) or enforced(e)
enforced(e) = (enforce_epoch != MAX and e >= enforce_epoch)
```

A build must satisfy, at compile time, for each of the two gates below:
`enforce_epoch == MAX`, or `accept_epoch != MAX` and
`accept_epoch + DUAL_ACCEPTANCE_MIN_EPOCHS <= enforce_epoch`, with
`DUAL_ACCEPTANCE_MIN_EPOCHS = 90` (one day). The floor exists to stop both
ends being armed at one epoch by mistake; the recommended window is longer
(see Activation recommendation).

### 2. Network-bound transfer signing (WT-03)

Constants (`crates/bloch-pos-committee/src/params.rs`):

| Constant | Role | Shipped value |
| --- | --- | --- |
| `SIGHASH_NETWORK_BINDING_ACCEPT_EPOCH` (new) | `A`: bound root accepted | `u64::MAX` |
| `SIGHASH_NETWORK_BINDING_ACTIVATION_EPOCH` (existing) | `E`: legacy root refused | `u64::MAX` |

Roots, for a transfer `tx` on a network whose committed genesis-manifest
digest is `D` (`CommittedState::admission_network_domain`, 32 bytes):

```
legacy(tx) = spend_signing_root(tx)                        (unchanged)
bound(tx)  = SHA3-256( DS_SPEND2 ‖ D ‖ legacy(tx) )
DS_SPEND2  = "BLCH4:SPEND2" ‖ 00 00 00 00                  (16 bytes)
```

Rule for a block of epoch `e`:

| Epoch | Roots a transfer may be authorised under |
| --- | --- |
| `e < A` | `legacy` only. Identical to every release so far, including the verifier calls and their order. |
| `A <= e < E` | Exactly one of `bound`, `legacy`, chosen by the first witness (below). On a state with no `D`: `legacy` only. |
| `e >= E` | `bound` only. On a state with no `D` every transfer is refused (`TransferReject::MissingNetworkBinding`). |

Choice of root inside the window. Let `w0` be the first witness in
transaction order (input 0 of a `Transfer`; entry 0 of the witness table of a
`TransferV2`). If `w0` verifies under `bound`, the transfer's root is
`bound`. Otherwise, if `w0` verifies under `legacy`, it is `legacy`.
Otherwise the transfer is refused (`BadSignature`). Every other witness must
verify under the transfer's root. A transfer whose witnesses are signed over
different roots is refused.

Unchanged: the wire encoding of both tags, `txid` (`SHA3-256(DS_TXID ‖
legacy(tx))`, so an output's key does not depend on which root was signed),
fees, the witness rules of `TransferV2`, signature suites and the transaction
signature policy. No state is added and the state root has no new component.

A joint transfer of the native-DEX rehearsal (`JointTransferContext`, feature
`native-dex-rehearsal`, not part of any release) keeps its own authorisation
root.

### 3. Signed commission cap (WT-04)

Constants:

| Constant | Role | Shipped value |
| --- | --- | --- |
| `DELEGATION_COMMISSION_CAP_ACCEPT_EPOCH` | `A`: tag `0x1C` accepted | `u64::MAX` |
| `DELEGATION_COMMISSION_CAP_ENFORCE_EPOCH` | `E`: tag `0x0E` refused | `u64::MAX` |

`A` must not precede `FUNDED_DELEGATION_ACTIVATION_EPOCH` (compile-time).

Wire format of `FundedDelegateV2`, little-endian, in order:

| Field | Bytes |
| --- | --- |
| tag `0x1C` | 1 |
| `network_domain` | 32 |
| `valid_until_epoch` | 8 |
| `funding_pubkey` (u32 length, then bytes) | 4 + n |
| input count (u32), then per input `txid` (32) and `vout` (4) | 4 + 36·k |
| `validator_pubkey_hash` | 32 |
| `amount_sat` (u128) | 16 |
| `change.value` (u64), `change.script_hash` | 8 + 32 |
| `max_base_fee_millisat_per_gas` (u128) | 16 |
| `tip_millisat_per_gas` (u128) | 16 |
| `tx_bytes` (u64) | 8 |
| **`max_commission_bps` (u128)** | 16 |
| `funding_signature` (u32 length, then bytes) | 4 + m |

Everything up to and including `max_commission_bps` is the intent. It is the
`FundedDelegate` intent with the tag byte `0x1C` and the cap appended.

```
signing_root = SHA3-256( "BLOCH:DELEGATION:FUND:V2" ‖ intent )
txid         = SHA3-256( DS_TXID ‖ signing_root )
tx_bytes     = len(intent) + 4 + ADMISSION_PQ_SIGNATURE_MAX     (16 above the 0x0E form)
```

Shape: every `FundedDelegate` shape rule, with `tx_bytes` as above, and
`max_commission_bps <= 10,000`.

Rules for a block of epoch `e` (funded delegation itself active):

| Epoch | `0x0E` (`FundedDelegate`) | `0x1C` (`FundedDelegateV2`) |
| --- | --- | --- |
| `e < A` | valid, unchanged | refused: `CommissionCapNotActive` |
| `A <= e < E` | valid, unchanged | valid |
| `e >= E` | refused: `CommissionCapRequired` | valid |

Admission of `0x1C` is the admission of `0x0E` with one added check, placed
after the validator is resolved and found eligible:

```
if validator.commission_bps > max_commission_bps: refuse CommissionAboveCap
```

A refusal spends nothing and creates nothing. The position created is the one
`0x0E` creates: the cap is not stored. It does not need to be, because of the
existing rule that stays in force: a commission increase is refused
(`CommissionIncreaseWithDelegations`) while any delegation to the validator
is queued, active or cooling down, starting in the block that admits it.
Admission at a commission no higher than the cap, followed by no increase
while the position exists, bounds the rate for the life of the position.

`FundedUndelegate`, `FundedDelegationWithdraw` and
`ValidatorCommissionUpdate` are unchanged. A position created by `0x0E` is
not changed at `A` or `E`.

### 4. Node policy (not consensus)

- **Mempool admission** judges a transaction under the rules of the wall
  epoch, as it does today. Inside the transfer window the first witness is
  tried under the bound root with a verification that draws on the sender's
  unit allowance but is not counted as a failure when it says no; the checks
  that follow are charged as usual. Outside the window admission makes the
  same verifier calls as before this GIP.
- **Selection.** The mempool records which transfers it authenticated under
  the legacy root while enforcement is scheduled. From the enforcement epoch
  the proposer leaves those out, and it leaves out `0x0E` requests; before
  acceptance it leaves out `0x1C` requests. Such entries age out through the
  ordinary retention rule. An entry that reaches a block anyway is refused by
  the transition and removed by the existing proposal-narrowing path.
- **`getchaininfo`** gains two additive fields:

```
"network_domain": "<64 hex>" | null,
"transaction_rules": {
  "transfer_network_binding": {
    "accept_epoch": <u64> | null, "enforce_epoch": <u64> | null,
    "accepted": <bool>, "required": <bool>,
    "domain_tag": "424c4348343a5350454e443200000000"
  },
  "delegation_commission_cap": {
    "accept_epoch": <u64> | null, "enforce_epoch": <u64> | null,
    "accepted": <bool>, "required": <bool>,
    "legacy_tag": "0x0e", "capped_tag": "0x1c", "max_commission_bps_limit": 10000
  }
}
```

  `accepted` and `required` are evaluated at the wall epoch. A signer uses the
  new form exactly when `accepted` is `true`. The receipt of
  `sendrawtransaction` names the new type `funded_delegate_v2`.

### 5. Signers

Rule for every signer: read `getchaininfo` from a node the signer trusts;
if the rule's `accepted` is `true`, sign the new form with that response's
`network_domain`; otherwise sign the old form.

In this repository:

- `bloch-pos funded-delegation prepare-delegate --max-commission BPS` writes
  the `0x1C` request; without the flag it writes `0x0E` as before. `inspect`
  shows `max_commission_bps` when present, `sign` binds the reviewed root of
  whichever form the file holds.
- `bloch-pos transfer-v2 --network-bound yes --genesis FILE` signs the bound
  root for that manifest's digest.
- `bloch-pos validator-payout ... --network-domain HEX32` does the same for
  the offline payout signer.
- Library: `PosTransaction::network_bound_signing_root(&domain)` (signer side,
  gate-independent) and `PosTransaction::spend_signing_roots_for_network`
  (the verifier's view at an epoch).

`tools/delegation-wallet-wasm` and the wallet CLI are not on the release
line this work is based on (`4f95205c`); they live on
`codex/wallet-delegation-protocol-20261003` and in the wallet repositories.
What they must change is listed under Migration.

## Rationale

### WT-03

**Why the genesis-manifest digest.** It is already committed in state, it is
what every newer transaction type binds (`network_domain` in funded deposits,
delegations, L2 and PQ-migration transactions), every node derives it from
the manifest it trusts, and two networks cannot share it unless they share
the whole manifest, clock and validator set included. A numeric chain id
would be a second identity to keep in step with the first.

**Why a second fold instead of a new preimage.** `bound = H(DS_SPEND2 ‖ D ‖
legacy)` keeps `legacy` as the single description of what a transfer does, so
the transaction id stays witness-free and identical under both roots, both
transfer formats share one rule, and a hardware or offline signer that
already computes `legacy` adds one hash.

**Why a window, and why this form of it.** A single epoch that switches the
root (the rule as it existed) invalidates, at that epoch, every signature
made a moment earlier and every signer not yet updated: exchanges with
withdrawal queues, offline payout signers, hardware flows. With a window a
signer upgrades on its own day and is protected from that day, since a
bound signature is valid on one network only regardless of what the other
network runs.

Three ways to tell, inside the window, which root a transfer was signed over:

| Option | Assessment |
| --- | --- |
| A marker in the encoding (new tags, or a flag in the transaction) | Unambiguous, no trial verification. Costs two new wire tags or a new field in both transfer variants, which touches every consumer of the transfer encoding (indexers, explorers, SDKs, exchanges that parse transfers) for a distinction that stops existing at `E`. |
| Accept a transfer if every witness verifies under either root, independently | No format change, but doubles the worst-case verification cost per witness and admits transfers with mixed roots, whose replay property is neither one. |
| **One root per transfer, chosen by the first witness** (chosen) | No format change. At most one extra verification per transfer, only for legacy-signed transfers, only inside the window. Mixed roots are refused. Deterministic. |

**Cost of the chosen form.** Inside the window a legacy-signed transfer costs
one verification more than it pays gas for (one hybrid verification per
transfer). A block full of single-input legacy transfers
costs at most twice the verification work of today for the length of the
window; multi-input transfers proportionally less. The cost disappears at
`E`. At the mempool door that extra verification is budgeted per source like
any other, and its failure is not charged to the relayer, because a
legacy-signed transfer is honest input inside the window.

### WT-04

Three designs were compared.

| | (a) Signed `max_commission_bps` in the request | (b) Notice period for increases, at least as long as leaving takes | (c) Both |
| --- | --- | --- | --- |
| Closes the race between signing and admission | Yes, exactly: the check and the bonding are one block | Only if the wallet also reads pending increases, and only for increases announced before signing | Yes |
| Protects a position after admission | Through the existing rule (no increase while a delegation exists) | Yes, by letting the delegator leave first | Yes |
| New committed state | None | Pending rate and effective epoch per validator, in the state root and the local cache | Same as (b) |
| Effect on validators | None | A validator with no delegators cannot reprice for about 23 days (cool-down 32 + withdrawal delay 2,048 epochs) | Same as (b) |
| What the delegator must trust | Its own signature | That its wallet displayed the pending increase | Its own signature |
| Wire change | One new tag | None for delegators; new semantics for `0x11` | Both |

**Chosen: (a).** The defect is a race between a signature and its admission.
A value inside the signature removes the race without depending on what a
wallet displayed or when. Design (b) alone leaves the request unpinned, adds
state to every validator, and makes an unbonded validator wait three weeks to
change a rate nobody is bonded to. Design (c) would be right if the chain
allowed commission increases while delegations exist; it does not, so the
notice period would protect against an event the existing rule already
forbids. If that rule is ever relaxed, a notice period of at least
`COOLDOWN_EPOCHS + WITHDRAWAL_DELAY_EPOCHS` must be added in the same change;
`CommissionIncreaseWithDelegations` is the invariant this GIP relies on, and
`after_admission_the_commission_cannot_rise_above_the_signed_cap` pins it.

**Why a new tag and not a version field.** The `0x0E` encoding has no spare
field and no version byte. A new tag is what an old node refuses at its
decoder and a new node refuses at its gate, which is the same verdict (an
invalid block) and the property every earlier format addition relied on.

**Why the cap is not stored.** Storing it per position would add a state
component and a local-cache section to carry a number that the existing
increase rule already makes unreachable.

**Why `0x0E` is refused from `E`.** As long as the capless form is valid a
wallet that was never updated keeps exposing its users. Refusing it makes the
protection a property of the network.

## Activation semantics

Both gates behave the same way; "old form" is a legacy-signed transfer or a
`0x0E` request, "new form" a bound-signed transfer or a `0x1C` request.

| Moment | Old form | New form |
| --- | --- | --- |
| Before `A` | valid | invalid |
| First block of epoch `A` | valid | valid |
| Last block of epoch `E - 1` | valid | valid |
| First block of epoch `E` | invalid | valid |

- **In flight at `A`.** Nothing that was valid becomes invalid. A new-form
  transaction submitted before `A` is refused at the mempool door and must be
  submitted again; it is not kept.
- **In flight at `E`.** An old-form transaction still unconfirmed at the first
  block of epoch `E` will never be included. For transfers the coins are
  untouched; the owner signs again over the bound root. For delegations the
  funding inputs are untouched; the owner signs a `0x1C` request. Pre-signed
  transfers held offline (cold-storage sweeps, emergency transactions,
  time-delayed payouts) stop being valid at `E` and must be re-signed before
  they are needed: this is the one user-visible cost, and the reason the
  window is announced.
- **Mempools.** See Node policy. No node needs a restart at either epoch.
- **Reorganisations across a boundary.** The rule is a function of the
  block's epoch alone, so a transaction's validity on a branch is the same on
  every node. A transaction can be valid in a block of epoch `E - 1` and
  invalid in a block of epoch `E` on a competing branch; that is true of every
  flag day.
- **Old nodes.** A node without this code follows the chain through `A` only
  until the first block that contains a bound-signed transfer or a `0x1C`
  request, which it rejects. Both `A` epochs are therefore hard-fork flag
  days for nodes, indexers and anything that replays blocks, although no user
  has to do anything at `A`.
- **History.** Blocks before `A` are judged under the old rule at their own
  epochs. A full-history replay with armed gates validates them unchanged.
  Both gates are listed in `GATES_UNARMED_IN_CANONICAL_HISTORY`, so a build
  that arms either at or below its release anchor refuses to start.

## Replay analysis (WT-03)

`D(X)` is network `X`'s genesis-manifest digest. Mainnet's is
`f47d3e49…311966`.

| Case | Before `A` | In the window | From `E` |
| --- | --- | --- | --- |
| Legacy-signed bytes from a network with another manifest (devnet, testnet, a relaunch from the same carryover), replayed on mainnet | accepted (the finding) | accepted | refused |
| Bound-signed bytes from that network, replayed on mainnet | refused | refused: `D` differs | refused |
| Mainnet bound-signed bytes replayed on that network | refused there if it has not armed; refused if armed (`D` differs) | same | same |
| Mainnet legacy-signed bytes replayed on a network that never arms | accepted there | accepted there | cannot exist on mainnet any more; old signatures still replay there |
| Two networks running the same manifest (a partition of one chain, or a private copy of mainnet's data directory run with the release binary) | not distinguished | not distinguished | not distinguished |

The last row is outside what a genesis binding can do: the two sides are the
same network by every committed value. Rehearsal builds refuse the mainnet
manifest, so such a copy can only run release rules. If a contentious fork of
one chain ever needs replay separation, the fork defines a new domain from its
fork epoch (`D' = H(D ‖ fork tag)`); the fold takes any 32-byte domain, and no
part of this GIP has to change.

A signer that has moved to the bound root is protected from that moment,
whatever epoch the other network is at. The wallet's "prove the RPC is
mainnet" check should stay until `E`, because until then a legacy signature
is still accepted and a wallet that has not been updated still produces one.

Funded deposits, the four funded-delegation messages, L2 deposits, DA batches,
withdrawal claims and the PQ-migration messages carry `network_domain` in
their signed intent and are not affected. The remaining lifecycle messages
(`ExitV2`, `RandaoRecommit`, KES registration and rotation, validator duty
signatures behind `VALIDATOR_NETWORK_BINDING_ACTIVATION_EPOCH`) were not
reviewed for this GIP.

## Backward compatibility

- With all four constants at `u64::MAX` this code changes no verdict. Tests
  pin it: the legacy root is the only root at every epoch
  (`with_the_window_unset_only_the_legacy_root_exists`), the verifier sees the
  historical call sequence
  (`with_the_window_unset_the_verifier_sees_the_historical_call_sequence`),
  the `0x0E` bytes and root are re-derived independently of the encoder
  (`the_capless_request_keeps_its_bytes_and_its_signing_root`), tag `0x1C` is
  refused (`with_the_cap_window_unset_only_the_capless_request_is_valid`), and
  the pre-existing invariance test `hf_gates_leave_transfers_byte_identical`
  and every pinned root in the suite still pass.
- **Existing delegations** are untouched at `A` and `E`: no migration, no
  re-signing, no change of rate. They keep the protection they have (no
  increase while they exist). Only the creation of new positions changes.
- **Indexers and explorers** must be rebuilt from the release that arms `A`
  (the indexer replays blocks through the consensus crate). `bloch-indexer`
  on this branch lists the three new constants and classifies `0x1C` as
  `funded_delegate_v2` with the ledger effect of `0x0E`.
- **Exchanges** that only receive and send transfers change one thing: the
  root they sign, by `E`.
- `PosTransaction::checked_signing_root(epoch)` (the compatibility helper
  that folds a source-tree label) is unchanged and still not the consensus
  path. Tools that call it must move to
  `network_bound_signing_root(&domain)` before `E`.

## Rollback

- **Before `A`.** Publish a release with the constants back at `u64::MAX`.
  Nothing happened on chain.
- **Inside the window, new forms not yet used on chain.** Same.
- **Inside the window, new forms on chain.** `A` cannot be withdrawn: blocks
  with bound signatures or `0x1C` requests are history and every node must
  keep validating them. `E` can be postponed or set back to `u64::MAX` in a
  release that reaches the fleet before `E`; the window then stays open and
  the only loss is that old-form transactions remain valid.
- **After `E`.** Moving `E` later would make blocks valid that current nodes
  reject and is a new fork; not a rollback. If enforcement proves harmful
  after `E`, the remedy is a new flag day that re-opens the old form from a
  future epoch.

This asymmetry (acceptance is permanent, enforcement is revocable until it
happens) is a second reason for the window: the irreversible step has no user
cost, and the step with a user cost stays reversible for the whole window.

## Security considerations

- **Extra verification inside the transfer window.** Bounded at one per
  transfer, unpaid, for the window only (see Rationale). At the mempool door
  it is budgeted per source and refused once a source has spent its failure
  allowance.
- **Root confusion.** A signature valid under both roots of one transfer
  would need `bound == legacy` (a SHA3-256 collision between differently
  tagged preimages) or one signature verifying two messages. The rule does
  not depend on either being impossible: it is deterministic in both cases.
- **Downgrade of a delegation.** The cap and the tag are inside the intent
  and the two forms have different domains, so a `0x1C` signature cannot be
  presented as `0x0E` or the reverse, and the cap cannot be edited
  (`a_capped_request_cannot_be_altered_downgraded_or_malformed`).
- **Griefing a capped request.** A validator can make a `0x1C` request fail
  by raising its commission above the cap. Nothing is spent; the delegator
  sees the new rate. A validator can also lower and raise its commission
  repeatedly while it has no delegators; `COMMISSION_UPDATE_LIMIT_ACTIVATION_EPOCH`
  (separate, inert) limits that to one update per epoch.
- **A cap the user did not choose.** A wallet that fills `max_commission_bps`
  with 10,000 gives its user nothing. The wallet must use the commission it
  displayed.
- **States without a network domain.** From `E` they refuse every transfer.
  Every network created by this code line has a domain; the case exists for
  old replay fixtures and fails closed.
- **Owner scope of 2026-10-20.** That decision excluded from scheduled
  releases anything that changes how users transfer. Arming WT-03 changes
  what a transfer signature must cover, so it needs an explicit decision that
  supersedes that scope. Neither gate is in `RELEASE_ARMABLE`.

## Activation recommendation

This is a recommendation. The epochs and the fork they ride with are the
owner's decision.

1. **Bundle both acceptance epochs into the next scheduled hard fork** after
   KES enforcement (8620), at one epoch `A` for both gates. Acceptance has no
   user cost and is the irreversible step, so it belongs with a release the
   whole fleet already has to install. `A >= publication epoch + 270` (72 h),
   the margin used for HF1.
2. **Enforce 630 epochs later** (`E = A + 630`, one week) for both gates. One
   week covers an exchange release cycle and a weekly cold-storage ceremony;
   the compile-time floor is 90. If an exchange or custodian asks for more,
   extend the window rather than skip it: `E` can move later in any release
   that ships before it.
3. **Order of upgrades.**
   1. Validators, archival nodes and RPC providers install the release
      (before `A`).
   2. Indexers and explorers rebuild from it (before `A`).
   3. Web wallet, extension, wallet CLI and the delegation WASM signer ship
      versions that follow `getchaininfo.transaction_rules` (before `A`; they
      switch by themselves at `A`).
   4. Announcement to exchanges, custodians and holders of pre-signed
      transfers at release time, repeated at `A`, with `E` as the deadline.
   5. Before `E`: confirm from an archival node that legacy-signed transfers
      and `0x0E` requests have stopped appearing in blocks for at least 90
      epochs, or postpone `E`.
4. **Before arming:** a mixed-fleet rehearsal with the
   `wallet-consensus-rehearsal` build through both boundaries on a
   development network, and a full-history replay of mainnet with the armed
   build (it must reproduce the canonical chain; both gates are above the
   anchor by construction).
