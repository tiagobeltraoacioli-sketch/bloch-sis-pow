# Advisor findings (3 lenses) — apply the HIGH/MED, defer LOW with a // TODO(sprint2) note


## Lens: protocol — verdict BLOCK — Two independent blockers: (1) the crate does not compile as assembled (router is written against sibling interfaces that don't match downstream/upstream/server, so the partition/forward path has never run), and (2) the core soundness claim is overstated — disjointness is NOT 'provable/by-construction' but rests on the node's UNENFORCED 32-bit extranonce1 (session.rs:367), with zero collision detection in the proxy; colliding workers silently duplicate all work. Plus a hard functional bug: reconnect never replays mining.authorize, so every post-reconnect share is rejected as unauthorized (session.rs:1094). Message shapes (subscribe/notify/set_difficulty/submit/set_extranonce, en2_size=4) are correct and job_id/submit pass-through is sound; fix the partition-guard, reconnect-authorize, metrics-double-count, and API-contract issues, then re-review.

- [HIGH] pool/src/types.rs (doc) + pool/src/upstream.rs + node src/stratum/session.rs:367-375
    issue: The central claim — per-worker extranonce1 spaces are 'provably DISJOINT / correct by construction' — is FALSE. Disjointness rests entirely on the node handing each upstream TCP session a distinct extranonce1, but the node derives it as the LOW 4 bytes of `id*0x9E3779B97F4A7C15 + now_micros` (session.rs:367). That is a 32-bit value with NO uniqueness registry and no collision check (the node comment literally says 'uniqueness is [required]' but never enforces it). Two workers that draw the same extranonce1 iterate the same extranonce2/nonce space and duplicate ALL work — the exact orphan/duplicate failure this pool exists to eliminate — silently. For the stated goal ('MANY miners/ASICs'), plus constant reconnect churn minting fresh sessions, birthday-bound collisions are a real, unbounded-over-time exposure. The proxy captures each worker's extranonce1 (WorkerInfo.extranonce1) but never cross-checks it against other active workers.
    fix:   Stop claiming 'provably disjoint / by construction' in the Cargo.toml, types.rs header, and upstream.rs docs — it is probabilistic on 32 bits. Add an actual guard: keep a process-wide `Mutex<HashSet<[u8;4]>>` (or String) of live extranonce1 values; when an upstream's SubscribeResult (or reconnect) yields an extranonce1 already in the set, force that upstream to drop+re-dial until it gets a unique one (bounded retries), and expose a `bloch_pool_extranonce1_collisions_total` metric. Only then is the partition sound.

- [HIGH] pool/src/router.rs (upstream EOF / is_transient reconnect arms) + pool/src/upstream.rs:reconnect
    issue: After any upstream reconnect the node session is Fresh->Subscribed but NOT Authorized, and the router NEVER re-sends mining.authorize. HandshakeReplay carries only {configure?, subscribe} (types.rs) and upstream.rs's own doc admits 're-sending mining.authorize is the router's responsibility' — but router.rs's reconnect arms only forward the returned handshake lines downstream; they never replay authorize upstream. The node requires is_authorized() for submit (session.rs:1094) and returns ErrorCode::Unauthorized (24) otherwise. Result: every share after an upstream reconnect is rejected as unauthorized until the miner happens to re-authorize (which it won't — it already did). A single upstream blip permanently breaks that worker's share submission.
    fix:   Capture the miner's mining.authorize line during the pump (store it on the worker, as the router already sees ClientMsg::Authorize) and, inside both reconnect arms, `upstream.send(&stored_authorize)` immediately after reconnect returns, before resuming the pump. Alternatively add `authorize: Option<Line>` to HandshakeReplay and replay it in upstream establish().

- [HIGH] pool/src/router.rs vs pool/src/downstream.rs / upstream.rs / server.rs
    issue: router.rs is written against 'assumed sibling interfaces' that do NOT match the actual modules, so the crate as assembled does not compile — meaning the reviewed pump logic (the partition/forward path) has never actually run. Concrete mismatches: (1) router calls `down.worker()` and `down.send()`, but DownstreamConn exposes a `pub worker` FIELD and `write()`, no such methods. (2) router calls `upstream.subscribe_result()`, `upstream.handshake_replies()`, `upstream.send()`, and `upstream.reconnect() -> Vec<Line>`; actual UpstreamConn has a `pub extranonce1` field, drains handshake via `read()` (prelude), `write()`, and `reconnect(&HandshakeReplay) -> SubscribeResult`. (3) server.rs calls `router::run_worker(id, stream, cfg, metrics)` but run_worker is `run_worker(down: DownstreamConn, cfg, metrics)` — server never constructs a DownstreamConn and passes a WorkerId+TcpStream instead. (4) downstream.rs's local `classify_client(raw)` calls `crate::codec::classify_client(raw)` with ONE arg, but codec's signature is `classify_client(line, worker)`.
    fix:   Reconcile one contract before merge: give DownstreamConn a `worker()` accessor (or have router read `.worker`), rename `send`->`write` (or add `send` aliases), have UpstreamConn expose `subscribe_result()`/handshake replies as the router expects OR rewrite router to drain the prelude via `read()` and build the set_extranonce line itself, fix run_worker's signature/call site to construct DownstreamConn::new(stream, id, cfg, metrics), and pass `worker` into codec::classify_client. Add a top-level integration test that stands up server+router+upstream against a mock node so this can't regress.

- [MED] pool/src/router.rs (ServerMsg::SubmitResult arm)
    issue: metrics.record_outcome(&outcome) is called for EVERY upstream response classified as SubmitResult, before the pending-share match. But upstream.rs/codec classify ANY bare boolean response as SubmitResult{Accepted} (parse_response Bool arm; the code comment even acknowledges authorize returns true). mining.authorize acks (`{id,result:true}`), mining.suggest_difficulty acks, and mining.extranonce.subscribe acks therefore each increment shares_accepted even though no share was submitted. shares_accepted is inflated by ~1 per worker (authorize) plus every suggest — corrupting the very accounting/PPLNS the pool is meant to provide.
    fix:   Only fold into metrics/accounting when the id matches a pending submit: move `metrics.record_outcome(&outcome)` INSIDE the `if let Some(pos) = pending.iter().position(...)` block, alongside `accounting.record`. Non-matching SubmitResults (authorize/suggest acks) must be forwarded downstream verbatim but NOT counted.

- [MED] pool/src/router.rs (reconnect arms) + pool/src/upstream.rs:reconnect
    issue: On reconnect the node assigns a NEW extranonce1 (fresh Session). The miner must be told via mining.set_extranonce or it keeps hashing with the stale extranonce1 -> all shares rejected as invalid PoW. But (a) upstream.reconnect returns a SubscribeResult and nobody builds/forwards a `mining.set_extranonce` notification from it, and (b) most ASICs only honor set_extranonce if they sent mining.extranonce.subscribe, which the proxy neither tracks nor requires. So a reconnect leaves the worker mining dead work. This is a liveness bug (not a collision-safety bug, since the node rejects stale-en1 shares), but it silently zeros the worker's output.
    fix:   On reconnect, if the fresh extranonce1 differs from the old one AND the miner subscribed to extranonce updates, push `mining.set_extranonce` downstream from the returned SubscribeResult. Otherwise the correct behavior is to DROP the downstream connection and let the miner reconnect+resubscribe (getting a clean subscribe-result with the new en1). Track whether the miner sent mining.extranonce.subscribe to decide. Document this explicitly.

- [LOW] pool/src/router.rs (keepalive arm) + pool/src/downstream.rs:keepalive_tick
    issue: Keepalive re-feeds the last cached mining.notify verbatim after idle. If that job has gone stale on the node (new template issued but proxy was idle only because the node also went quiet), the miner resumes an old job and produces stale shares (error 21). The cached notify may also have clean_jobs=true, which on re-feed tells the miner to abandon current work for a job that is itself stale. Matches the reference python proxy behavior, so acceptable for MVP, but it means keepalive can manufacture stale rejects.
    fix:   Acceptable to ship, but note it: prefer re-feeding only when the cached job age < a staleness bound, and consider stripping/forcing clean_jobs=false on the re-fed copy so it does not trigger a work reset on a stale template.

- [LOW] pool/Cargo.toml + pool/src/*
    issue: The deliverable path pool/ already contains a DIFFERENT pool scaffold (Cargo.toml README + src/ with a getblocktemplate/bloch-crypto native pool, confirmed present on disk). Dropping this crate's Cargo.toml/src at pool/ overwrites or collides with the existing crate; the header comment admits this ('a prior, different pool scaffold already exists at pool/'). The task also requires NOT modifying existing files.
    fix:   Place this proxy in a distinct directory (e.g. pool-proxy/ or pool/proxy/ with its own [workspace]) so it neither overwrites the existing native pool nor gets pulled into the consensus workspace, and state the final path in the integration notes.


## Lens: security — verdict BLOCK — two HIGH issues must be fixed before deploy: (1) no downstream handshake/idle timeout is a trivial slowloris DoS that pins all max_workers slots, and (2) upstream reconnect never re-sends mining.authorize, so after any node blip the miner silently gets no jobs and all submits are rejected as Unauthorized (confirmed against node src/stratum/session.rs). Also note the crate does not compile as assembled (router's assumed sibling interface != actual module APIs), so the hostile-input pump is currently untested. Panic-safety of the parsing/framing layer itself (codec/downstream/upstream) is otherwise solid: all network-facing parsers return Result/Option with bounded MAX_LINE_BYTES framing and no unwrap/expect/indexing on untrusted input; pending/PPLNS/pre-subscribe buffers are all capped.

- [HIGH] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/router.rs (run_worker / read_handshake) and pool/src/server.rs (accept loop)
    issue: Slowloris capacity-exhaustion DoS: there is NO idle/handshake read timeout anywhere on the downstream path. WorkerGuard increments workers_active the instant a task is spawned, and read_handshake() awaits down.read() indefinitely. A peer that connects and sends nothing (or trickles < PRE_SUBSCRIBE_CAP lines slowly, or sends bytes with no '\n') never trips MAX_LINE_BYTES or PRE_SUBSCRIBE_CAP and never releases its slot. Opening max_workers (default 4096) silent sockets permanently pins every slot, and each also holds a task + upstream-less buffer, locking out all legitimate miners. Note the node's own stratum enforces an auth_deadline (session.rs:683) precisely to prevent this — the proxy dropped that protection.
    fix:   Wrap the whole handshake in a bounded timeout, e.g. `tokio::time::timeout(cfg.connect_timeout, read_handshake(&mut down, worker)).await` (map elapsed -> PoolError::Timeout and drop the worker). Additionally give downstream reads in the pump a liveness ceiling. Add a config field (e.g. handshake_timeout, default 15s) rather than reusing connect_timeout if you want them independent.

- [HIGH] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/router.rs (upstream EOF / is_transient reconnect arms) and pool/src/upstream.rs (reconnect)
    issue: After ANY upstream reconnect the node connection is Subscribed-but-NOT-Authorized. HandshakeReplay only carries configure?+subscribe (upstream.rs docstring admits this), and the router's reconnect arms only re-forward subscribe/set_extranonce replies — they never re-send mining.authorize. Verified against the node: the stratum state machine is subscribe -> authorize -> authorized (session.rs:11), and install_fresh_template bails on an un-authorized session (session.rs:64 'install_fresh_template called on un-authorized session'). So after a transient node blip the worker's new upstream receives NO jobs and every subsequent mining.submit is rejected as Unauthorized (err 24) — the miner silently earns nothing with no teardown/alert. This directly violates the 'graceful reconnect without dropping downstream' goal.
    fix:   Persist the miner's authorize line during handshake (DownstreamConn already captures info.authorized_user; better: store the raw authorize Line) and, inside reconnect after the fresh SubscribeResult, replay mining.authorize upstream before resuming the pump. Gate resuming submits until the authorize ack is seen.

- [MED] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/router.rs (pump, ServerMsg::SubmitResult arm) + pool/src/upstream.rs parse_response / pool/src/codec.rs classify_server
    issue: Share-accounting integrity: the codec/upstream classify EVERY bare boolean response as SubmitResult{Accepted} (they cannot distinguish a submit ack from an authorize/configure/suggest_difficulty ack, as their own comments note). The router then calls `metrics.record_outcome(&outcome)` UNCONDITIONALLY before doing the id-correlation to a pending share. Result: mining.authorize / mining.configure / suggest_difficulty acks each inflate bloch_pool_shares_accepted_total by one, corrupting the headline pool metric and any hashrate/payout inference built on it. (Accounting.record is correctly gated on a pending match; only the metric is wrong.)
    fix:   Move `metrics.record_outcome(&outcome)` INSIDE the `if let Some(pos) = pending.iter().position(...)` block so the counter is bumped only when the id actually matches a forwarded submit. The else-branch should just log, not count.

- [MED] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/router.rs (pump: `upstream.send(&raw).await?` in the down.read arm)
    issue: Asymmetric failure handling drops miners on upstream write faults. Downstream->upstream forwarding uses `?`, so if the node has closed and the very next miner line (e.g. a mining.submit) fails to write upstream, run_worker returns Err and the downstream miner is torn down instead of reconnecting. Reconnect is only attempted on the upstream READ EOF/transient branch, not on write errors — so a node restart that is noticed via a failed forward-write (common) kills the worker rather than recovering it.
    fix:   Handle write failures symmetrically: match on upstream.send() result; if is_transient(&e), run the same reconnect path (reconnect + re-forward replies + re-authorize + reset keepalive) and, if desired, re-forward the just-read raw line, instead of propagating with `?`.

- [MED] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/router.rs vs pool/src/downstream.rs / pool/src/upstream.rs / pool/src/server.rs
    issue: The crate as assembled does not compile: the reviewed pump is written against an ASSUMED sibling interface that the actual modules do not expose, so its panic-safety and reconnect logic are unverified by tests. Concretely: server.rs calls `router::run_worker(id, stream, cfg, metrics)` (WorkerId + TcpStream) but router defines `run_worker(down: DownstreamConn, cfg, metrics)`; router calls `down.worker()` / `down.send()` (actual: field `down.worker`, method `write()`), and `upstream.subscribe_result()` / `handshake_replies()` / no-arg `reconnect() -> Vec<Line>` (actual: field `extranonce1`, buffered prelude via `read()`, `reconnect(&HandshakeReplay) -> Result<SubscribeResult>`). Until wired, no integration/adversarial test exercises the hostile-input pump at all.
    fix:   Reconcile the signatures: have server construct DownstreamConn and pass it (or have run_worker take stream and build it); replace `down.worker()`->`down.worker`, `down.send`->`down.write`, `upstream.subscribe_result()`->`&upstream.extranonce1`, drive handshake replies from the upstream prelude via read(), and pass the stored HandshakeReplay into reconnect(). Then add an end-to-end mock-node test that feeds malformed/oversize/partial lines through the real pump.

- [LOW] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/downstream.rs (write(), keepalive substring gate)
    issue: Keepalive job cache is poisoned by a substring test: `if line.contains(methods::NOTIFY)` treats ANY downstream line containing 'mining.notify' as the last job. The node's mining.subscribe RESULT literally embeds 'mining.notify' inside its subscriptions array ([["mining.set_difficulty",en1],["mining.notify",en1]],...), so the subscribe-result line is cached as last_notify_raw and would be re-fed to the miner on idle via keepalive_tick() — feeding a subscribe response where a job is expected. (Latent because the integrated router keeps its own last_notify_raw set only on ServerMsg::Notify, but downstream.keepalive_tick() is public and used in tests.)
    fix:   Gate on the parsed classification, not a substring: only cache when the line classifies as ServerMsg::Notify (or method_of(line) == Some("mining.notify") exactly), not on a `contains` check. Remove one of the two duplicate keepalive implementations to avoid divergence.

- [LOW] /Users/tiagoacioli/dev/BlochSISPoW-project/pool/src/metrics.rs (handle_conn / serve_metrics_on)
    issue: The metrics HTTP endpoint has no per-connection read timeout and no concurrency cap. handle_conn loops on stream.read() until \r\n\r\n or MAX_REQUEST_BYTES; a peer that opens a socket and sends 1 byte then stalls holds a spawned task indefinitely (never reaching the 8KB cap). Unbounded such connections exhaust tasks/fds. Bind default is 127.0.0.1 so blast radius is local, but operators exposing metrics widen it.
    fix:   Wrap the read-head loop in tokio::time::timeout (e.g. 5s) and drop on elapse; optionally bound in-flight metrics connections with a semaphore. Also fix contains_head_end to check across the accumulated buffer, not only the latest chunk, so the end-of-head marker isn't missed when split across reads.

- [HIGH] pool/src/router.rs (run_worker body)
    issue: Router codes against a fictional sibling API that does not match downstream.rs/upstream.rs; multiple hard compile errors. Specifically: `down.worker()` — DownstreamConn exposes a public FIELD `worker`, not a method. `down.send(&line)` and `upstream.send(&raw)` — the real method is `write(&mut self, &str)`, there is no `send`. `upstream.subscribe_result().extranonce1` — UpstreamConn has no `subscribe_result()`; it exposes a public field `extranonce1` and `extranonce2_size`. `upstream.handshake_replies().to_vec()` — no such method exists; the node's subscribe-result/notify prelude is delivered only via `UpstreamConn::read()` draining its private `prelude` queue. `upstream.reconnect()` — router calls it with NO args expecting `Result<Vec<Line>>`, but the real signature is `reconnect(&mut self, replay: &HandshakeReplay) -> Result<SubscribeResult, PoolError>`.

Keep `replay` alive across the loop for reconnect.

- [MED] pool/src/router.rs (ServerMsg::SubmitResult arm)
    issue: Share-accept metric is inflated by every non-submit boolean response. In upstream.rs::parse_response, ANY `{result:true}` reply (mining.authorize, mining.configure, mining.suggest_difficulty) is classified as ServerMsg::SubmitResult{outcome:Accepted}. In router the SubmitResult arm calls `metrics.record_outcome(&outcome)` UNCONDITIONALLY, BEFORE the id-vs-pending correlation check. The 'router disambiguates by id' claim only guards the PPLNS window, not the Prometheus counter.
    fix:   Move `metrics.record_outcome(&outcome)` INSIDE the `if let Some(pos) = pending.iter().position(...)` block, so only responses that correlate to a forwarded mining.submit are counted. Log the else-branch (non-submit ack) without touching counters.

- [MED] pool/src/downstream.rs (read_line_bounded)
    issue: Cancel-safety contract is violated — router.rs explicitly documents `down.read()` MUST be cancel-safe (partial line retained in the conn buffer) because it is polled inside tokio::select!. But read_line_bounded accumulates into a LOCAL `let mut line: Vec<u8>`; on the no-newline branch it does `self.reader.consume(n)` (permanently removing those bytes from the BufReader) and then awaits `fill_buf()` again. If the select! arm is cancelled at that await (because the upstream or keepalive branch fires), the `line` accumulator is dropped and the already-consumed partial bytes are lost → stream desync, corrupting or dropping the next miner line (potentially a mining.submit).
    fix:   Persist the partial-line accumulator on the struct (like codec::LineReader's `buf` field) so a dropped read future loses nothing, OR wrap the read in a form that only consumes bytes up to and including a full line. Simplest: replace downstream's bespoke reader with the already-cancel-safe crate::codec::LineReader over the OwnedReadHalf and reuse it.

- [MED] pool/src/router.rs (reconnect path) / pool/src/upstream.rs (reconnect doc)

Post-reconnect, every mining.submit the node receives on the fresh connection is rejected (error 24 unauthorized), silently killing that worker's shares until the process restarts.
    fix:   Capture the miner's mining.authorize raw line during read_handshake (store it alongside HandshakeReplay), and after a successful upstream.reconnect re-send it via upstream.write(&authorize_line) before resuming the pump.
