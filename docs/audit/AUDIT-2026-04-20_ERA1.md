## Post-release findings (discovered in production after v0.5.11)

### PR-2 (Sprint DD) — Mining path writes no UndoData, blocking reorg recovery ✅ RESOLVED

**Discovered:** 2026-04-21, immediately after Sprint CC enabled IBD
on the Akash worker. Severity in practice: **HIGH** (any node that
mines locally before fully syncing gets stuck as soon as IBD delivers
a heavier chain).

**What it looked like:** Worker boots, generates genesis locally
(correct — deterministic), mines one block h=1 locally (correct —
no peers yet). A minute later IBD finally kicks in (thanks to Sprint
CC) and the seed delivers 500 real mainnet blocks including competing
blocks at h=1 with more blue_work. The worker computes a reorg plan:
rollback [local_h=1], apply [seed_h=1]. Rollback fails immediately
with `rollback_block: no undo data for block 00000000..`. Every
subsequent IBD block triggers a reorg attempt that fails with the
same error on the block just before it, cascading indefinitely. The
worker stays at `height: 1` forever, now with its own chain that
nobody else considers canonical.

**Root cause:** The miner loop in `src/main.rs` (the `Ok(r) if r.found`
branch after `mining::mine_block`) was written before Sprint U landed
and still applied UTXO/tx_index/coinbase mutations inline: it called
`store.put_tx_index`, `put_utxo`, `put_coinbase_info`, `delete_utxo`
directly, but never called `put_undo_data`. Every accept_block path
for a non-mined block (Extension, Reorg re-apply) had been migrated
to route through `reorg::apply_block_utxo_mutations` which records
UndoData as a byproduct of the same forward mutations — but the miner
loop was missed in that migration.

Consequence: a locally-mined block is unrollback-able. Reorgs that
need to rewind past any locally-mined block abort with
`no undo data for block ..`, and `execute_reorg` returns
`storage in partial state` — which under the current accept_block
error path means the block that triggered the reorg is rejected
rather than accepted. Worker never advances.

This did not matter before Sprint CC because, before that fix,
IBD never actually happened — peers never learned each other's real
tips, so the reorg path was never exercised on a worker that had
mined locally. The two bugs masked each other.

**Fix (this sprint):**

  src/main.rs
    - Miner loop replaced the inline mutation block (put_tx_index /
      put_utxo / put_coinbase_info / delete_utxo loops) with a single
      call to `reorg::apply_block_utxo_mutations(&store_m, &block)`.
      Same forward effects on the UTXO set, tx_index, and coinbase
      info — but with `put_undo_data` written as a byproduct.
    - Error path: partial-failure warn! preserved. The miner loop
      MUST NOT abort on a storage error here, because the alternative
      is a frozen miner. Better to log and keep mining.

  tests/sprint_dd_mined_undo.rs (new)
    - mined_block_writes_undo_data_on_apply — builds a synthetic
      miner-shaped block (coinbase-only on top of genesis) and asserts
      that `get_undo_data(&hash)` returns Some after
      apply_block_utxo_mutations. The undo record's shape (one
      tx_index key, one created UTXO, one coinbase txid, zero spent
      UTXOs) is verified field-by-field so a future refactor that
      silently drops one of them fails the test.
    - mined_block_round_trip_rolls_back_cleanly — full apply → rollback
      round trip on the synthetic mined block. Pre-Sprint-DD this test
      would have failed at rollback_block with the exact error observed
      in production. Post-fix, rollback succeeds, the coinbase UTXO is
      removed, and the undo record is consumed.

**Consensus-preservation:** zero. Same UTXO/tx_index/coinbase
mutations in the same order, same block hash, same gossipsub wire
message. Only the addition of an UndoData record in CF_UNDO, which
is a local storage concern invisible to peers. Pre-Sprint-DD nodes
interoperate with post-Sprint-DD nodes at the protocol level; only
their own reorg recovery differs.

**Test suite delta:** +2 tests in `tests/sprint_dd_mined_undo.rs`.
Total 178 passing post-Sprint-DD.

### PR-1 (Sprint CC) — `my_tip` captured at startup, never refreshed ✅ RESOLVED

**Discovered:** 2026-04-21, immediately after the v0.5.11 seed
redeployment. Severity in practice: **HIGH** (breaks new-peer sync
against any node that has built blocks after startup).

**What it looked like:** The Njalla seed was running v0.5.11 at
height=2655. A new Akash worker also running v0.5.11 booted, dialed
the seed, established a gossipsub connection (confirmed on both
sides), and then sat at height=1 for tens of minutes, mining its
own isolated chain. The seed logs never showed an IBD exchange; the
worker logs never showed one either. Both sides looked superficially
healthy — `peers: 1` on each — but no `PeerTip` exchange reflecting
reality ever took place.

**Root cause:** `network::run` signature took `our_blue_score: u64`
and `our_height: u64` as values. These were captured once at
startup in `main.rs` (from `dag.read().tip_blue_score()` and
`.block_count()`), then baked into a `my_tip` `NetworkMessage::PeerTip`
struct constructed once at the top of `run` and reused verbatim
whenever a peer connected. Any subsequent growth of the local DAG —
whether from mining locally or from gossipsub-received blocks — did
not update the published tip. A seed that had grown to height=2655
by accepting gossiped blocks still told every new peer "I'm at
height=1".

Once the peer saw `height=1` from the seed's `PeerTip`, its IBD
trigger (in `main.rs` line 313: `if peer_s > our_s { GetHeaders... }`)
did not fire, because the peer's own height (also 1 on first boot)
was not less than 1. Both sides stayed quiet, and the gossipsub
`NewBlock` channel alone kept producing the appearance of a live
network for users only watching real-time activity.

**Why the audit missed this:** The audit was a static-analysis /
code-reading pass; the bug requires a multi-node runtime to
manifest. Every unit and integration test constructs a single DAG,
never a pair exchanging `PeerTip`. Sprint R's network-stability
work had touched the same function without hitting this because
sprintr's mining was driven by worker nodes always freshly
initialized against genesis, which happened to match the stale
`my_tip` announced back by the seed.

**Fix (this sprint):**

  src/network/mod.rs
    - `NetworkNode::run` signature changed: previously took
      `our_blue_score: u64, our_height: u64`; now takes
      `dag: Arc<RwLock<GhostDAG>>`. All tip-related reads happen
      through the lock.
    - New free function `build_current_tip(&Arc<RwLock<GhostDAG>>, &str)
      -> NetworkMessage` reads the DAG under a short read lock and
      emits a `PeerTip` reflecting the current tip. Called from both
      `ConnectionEstablished` (preserving the existing IBD trigger
      path) and from a new 60-second `tip_announce` timer.
    - New `tip_announce` tokio interval fires every 60s and
      re-publishes the current tip to the sync topic whenever there
      is at least one connected peer. This ensures peers that
      connected before new blocks were accepted still learn the tip
      has advanced, without having to disconnect-and-reconnect.
    - Three regression tests in the existing #[cfg(test)] mod:
        * `build_current_tip_reads_fresh_dag_state_each_call` — the
          canary. Builds a tip, advances the DAG, builds another tip,
          asserts the second tip reflects the new height/blue_score.
          If someone reintroduces caching, this fails.
        * `build_current_tip_preserves_peer_id` — trivial structural
          check that the peer_id string round-trips.
        * `tip_announce_interval_is_bounded` — documents the
          acceptable range for the periodic tip-announce interval
          (10s min, 300s max) so someone accidentally setting it to
          the wrong order of magnitude gets caught.

  src/main.rs
    - `node.run(block_tx, outbound_rx, our_score, our_count)` →
      `node.run(block_tx, outbound_rx, dag.clone())`. The existing
      `our_score` / `our_count` variables stay alive to initialize
      `NodeState` (which is read-only display state) — only the
      network plumbing switches to the live DAG handle.

**Test suite delta:** +3 tests in `src/network/mod.rs::tests`.
Total 176 passing post-Sprint-CC (up from 173 post-Sprint-BB).

**Why this isn't numbered as a CRITICAL/HIGH/MEDIUM audit finding:**
The original audit enumerated 25 findings and has been closed at
88%. New findings discovered after the audit's scope closes go into
this "Post-release" section so the original scoreboard remains
faithful to the audit's actual scope. PR-1 is tracked here with
equivalent rigor.

## CRITICAL findings

### C-1 — `accept_block` is forward-only, UTXO state diverges on reorg ✅ RESOLVED

**Original description:** `accept_block` applies UTXO mutations for
every accepted block forward-only — there is no mechanism to undo
UTXO when a block previously classified as `blue` becomes `red` after
new blocks arrive and change the DAG structure. In PHANTOM/GhostDAG,
`mergeset_blues` is reclassified as new blocks merge conflicting
paths. Kaspa-real computes UTXO against a "virtual block" that is
recomputed when the virtual changes; GroundState persisted UTXO
per-block, assuming blocks are final at arrival — valid for Bitcoin,
**invalid for GhostDAG**.

The attack path: attacker creates block X with tx consuming UTXO U,
then builds a parallel branch that demotes X to red via anticone. U
remains marked as spent in storage, but X is no longer in the blue
set of the virtual block. A new tx can now consume U again in block
Y and pass validation because storage never reverted.

**Status:** Resolved across Sprints U.1 → U.4, merged 2026-04-21.

- **U.1** (commit `18db5ef`) — `UndoData` struct + `CF_UNDO` column
  family + undo capture in `accept_block`.
- **U.2** (commit `3a2bb99`) — `Storage::rollback_block(hash)` that
  consumes an `UndoData` record and replays mutations in reverse.
- **U.3** (commit `e2190dc`) — `src/reorg.rs` with pure
  `find_lca` / `compute_reorg_plan` / `apply_block_utxo_mutations` /
  `execute_reorg`.
- **U.4** (commit `ff675e3`) — 4-way disposition dispatcher in
  `accept_block` (Extension / ForkLoser / Reorg / Unexpected). Block
  bodies persisted unconditionally to `CF_BLOCKS` so fork-losers
  can be brought in by a future reorg without re-download.

**Test coverage (52 tests pinning the fix):**
9 in `tests/sprint_u1_undo_data.rs` · 10 in `tests/sprint_u2_rollback.rs`
(including `apply_rollback_apply_rollback_is_stable` which proves
byte-identical round trips) · 16 in `tests/sprint_u3_reorg.rs` ·
5 in `tests/sprint_u4_reorg_e2e.rs` (including a flip-flop
`A(2) → B(3) → A(5)` double reorg).
Full suite: **154 passed, 0 failed**.

**Known restriction:** transactions are validated against the UTXO
set at *accept time* (pre-reorg). Signatures are checked against the
current chain, not the chain the block eventually joins. The block
is still structurally valid and gets re-examined for UTXO
consistency when the reorg actually happens. Deferred to a future
sprint for post-reorg semantic revalidation.

### C-2 — `generate_keypair_from_seed()` was a declared stub ✅ RESOLVED

**Original description:** The function validated seed length but
**ignored the seed** and returned a random keypair
(`mldsa65::keypair()` with no seeding). Any code depending on
deterministic key derivation (BIP39 recovery, HD wallet) was
silently broken. `bip39 = "2"` in `Cargo.toml` created the illusion
of working recovery — a user backing up a mnemonic would lose funds
on restore because the restored wallet would be a different keypair.

**Status:** Resolved in Sprint T.1, merged 2026-04-21 (commit `b39284a`).

- Forked `rustpq/pqcrypto` to `Groundstate100/pqcrypto-fork` branch
  `main`. Strict superset of upstream v0.2.11.
- Added `with_seeded_rng(&[u8; 32]) -> SeededRngGuard` RAII API to
  `pqcrypto-internals` that overrides the internal RNG for the
  guard's lifetime, then restores OS CSPRNG on drop.
- `crypto::generate_keypair_from_seed(seed)` now produces
  byte-identical `(pubkey, secret_key)` pairs for the same 32-byte
  seed across calls and across platforms.

**Test coverage:** `tests/sprint_t1_seed_determinism.rs` — 5 tests.

### C-3 — CVE-2012-2459 (duplicate-tx merkle malleability) ✅ RESOLVED

**Original description:** The merkle root calculation duplicates the
last hash when the list is odd-length (Bitcoin-style). This means
`[A, B, C]` and `[A, B, C, C]` produce the same merkle root. An
attacker could construct `B1 = [coinbase, A, B, C]` and
`B2 = [coinbase, A, B, C, C]` with identical headers and propagate
both — half the network accepts `B1` and the other half `B2`, each
producing different UTXO sets, **causing a consensus split**.

**Status:** Resolved in Sprint S, merged 2026-04-21 (commit `e040173`).

Added `validate_no_duplicate_txs` pass in
`validate_tx_in_block_with_maturity` that builds a `HashSet` of
`(prev_txid, prev_index)` pairs for the block being validated and
rejects the block on collision. Runs before any storage mutation.

**Test coverage:** `tests/security_audit.rs` —
`vuln08_validate_structure_enforces_no_duplicate_txs`,
`vuln08_duplicate_tx_merkle_collision_is_rejected`.

### H-2 — ML-DSA-65 size constants were wrong in `core::mod` ✅ RESOLVED

**Original description:** Two different size sets coexisted in the
codebase — `core/mod.rs` had `PRIVKEY_SIZE = 4000` and

comparing the constants against `pqcrypto_mldsa::mldsa65::*` sizes

### H-3 — libp2p identity uses Ed25519 (classical), not PQ ✅ RESOLVED

**Original description:** The P2P identity that signs the Kyber
handshake transcript is Ed25519
(`identity::Keypair::generate_ed25519()` in `src/network/mod.rs:553`),
but the public landing page markets "ML-KEM-768 hybrid post-quantum
transport" without distinguishing KEM from signatures. A casual
reader concludes the entire transport is PQ. In practice, a future
quantum adversary could break Ed25519, forge peer identity, and
MITM — the confidentiality of previously-captured messages stays
protected by Kyber (harvest-now fails), but **future connections
are vulnerable**.

**Status:** Resolved in Sprint W. Documentation-only fix (a full
code-path swap would require forking libp2p — out of scope).

Changes applied:
- `README.md` Security section now has an explicit "Hybrid
  post-quantum transport" subsection with a per-primitive breakdown
  (confidentiality PQ, identity classical) and a spelled-out threat
  model for active quantum MITM on new connections.
- `docs/index.html` landing page: the Key-Exchange protocol card
  now calls out "hybrid PQ design" and mentions Ed25519 identity
  explicitly; the architecture table says
  `Kyber768 (hybrid + Ed25519 auth)`.
- `FIRST_POST_QUANTUM_HANDSHAKE.md` (source for the public PDF):
  the Cryptographic-stack section now lists peer-identity
  authentication as a separate entry marked "classical, not
  post-quantum", and a new Hybrid-model section explains the
  TLS-1.3-hybrid analogy and the harvest-now-decrypt-later

### H-4 — PDF claims "AES-256-GCM" but code uses ChaCha20-Poly1305 ✅ RESOLVED

**Original description:** `FIRST_POST_QUANTUM_HANDSHAKE.pdf` says
*"Session encryption: AES-256-GCM (random 96-bit nonce) NIST SP
800-38D"*. The actual code (`src/transport/mod.rs:455`) uses
`ChaCha20Poly1305` with a counter-derived nonce. Both are secure
AEADs and ChaCha20-Poly1305 with a counter is strictly more secure
than AES-GCM with a random nonce (no collision risk until 2^64
messages vs birthday bound of ~2^48 for AES-GCM random). **But the
public claim is factually wrong** — an external auditor will flag it
immediately.

**Status:** Resolved in Sprint W.

- `FIRST_POST_QUANTUM_HANDSHAKE.md` (PDF source) now says
  "ChaCha20-Poly1305 (RFC 7539) with counter-derived 96-bit nonces".
  **The PDF should be re-exported from this source and the old
  artifact replaced on the public-facing page.**
- `README.md` architecture and security tables now list
  "ChaCha20-Poly1305 (RFC 7539)" for the session cipher, distinct
  from AES-256-GCM which is correctly used for wallet-at-rest
  encryption.
- `docs/index.html` landing page architecture table has a new row
  explicitly naming the session cipher
  (`ChaCha20-Poly1305 · RFC 7539`).

### H-5 — `past_blue_set` bounded to 2*K=20 underestimates anticone ⏳ PENDING (Sprint V)

**Original description:** `src/consensus/mod.rs:513-531` bounds the
`past_blue_set` walk at `self.k * 2` — with `K = 10`, this is only
20 selected-chain hops. Used in `classify_mergeset` to seed the
blue_set against which PHANTOM's K-constraint is evaluated. If a
mergeset block has an anticone intersecting blues **beyond 20
blocks**, the count is under-estimated → a red block is classified
as blue → `blue_score` diverges between nodes.

In a network with latency over 20 × 10s = 200 seconds, or during an
honest partition that lasts long, different nodes will disagree on
the blue/red classification of older blocks. **This is a silent
consensus split.**

Kaspa-real solves this with a reachability tree (interval tree
indexing) for O(1) ancestor checks without a depth bound. The bound
here was chosen for performance but leaks as a correctness bug at
high latency.

**Remediation plan (Sprint V):**
Two options under evaluation:
1. **Short-term mitigation** — raise the bound to `K * 100 = 1000`
   and add a warning log when the bound is hit. Low risk, buys time
   for option 2.
2. **Long-term fix** — implement a Kaspa-style reachability tree for
   true O(1) ancestor queries.

Sprint V will ship option 1 (short-term mitigation) and schedule
option 2 as a multi-sprint project.

**Status:** In Sprint V pipeline.

### H-6 — `FINALITY_DEPTH` in `is_final()` diverged from `CHECKPOINT_DEPTH` ✅ RESOLVED

**Original description:** `consensus/mod.rs::is_final()` used a
local `const FINALITY_DEPTH: u64 = 86_400` (roughly 10 days at 10s
block time), while `main.rs` updated `finalized_height` using
`CHECKPOINT_DEPTH = 1_000` (~2.7 h). RPC queries on `is_final`
returned false for 10 days while the node internally treated blocks
as final after 1000 blue_score — a visible discrepancy for users
and integrating exchanges. The README said "Finality depth 1,000
blocks", agreeing with `CHECKPOINT_DEPTH` and disagreeing with
`is_final()`.

**Status:** Resolved in Sprint S (commit `e040173`).

`consensus/mod.rs::is_final()` now uses `crate::core::CHECKPOINT_DEPTH`
as the single source of truth. See inline comment at
`consensus/mod.rs:597-601` for the pre-fix history.

### M-2 — `load_persisted()` trusts RocksDB without re-validation ✅ RESOLVED

**Original description:** `consensus/mod.rs:339-350` reconstitutes
the DAG from storage without recomputing PHANTOM. If RocksDB is
corrupted or someone with disk access edits `blue_score` /
`mergeset_blues`, the node restarts with arbitrary consensus.
Defense-in-depth: either recompute PHANTOM on load, or hash-chain
over `GhostdagData` and verify at load time.

**Status:** Fixed in Sprint Y. A separate column family
`CF_DAG_INTEGRITY` now stores a hash-chain link (SHA-256) per
block, computed as
`H(block_hash || canonical_encode(gdata) || parent_integrity_hash)`.
Genesis anchors with an all-zero parent. On boot,
`load_persisted_validated` re-derives each link and compares against
what was stored. Any mismatch is fatal: the node logs the offending
block and exits, leaving the operator to investigate.

Three layers of the defense are tested:

1. **Canonical encoding determinism.** Two `GhostdagData` values that
   differ only in `HashMap` iteration order produce byte-identical
   pre-images. Without this, two nodes with different hasher seeds
   would produce different integrity hashes for the same block.
2. **Happy-path validation.** A DAG written via the new
   `put_dag_with_integrity` loads successfully, with
   `self_healed: false`.
3. **Tampering detection.** Altering `blue_score`, `mergeset_blues`,
   or any other field in CF_DAG without updating the integrity record
   triggers `ChainMismatch`. Swapping the integrity hash itself also
   triggers it. Partial coverage (some integrity records missing)
   triggers `PartialCoverage` — we refuse rather than silently
   self-heal, because targeted deletion looks identical to a crash
   mid-migration and the conservative choice is to surface both.

**Migration path:** Pre-Sprint-Y databases have an empty
CF_DAG_INTEGRITY. The loader detects this (all records absent, not
some), computes fresh integrity hashes from the existing
GhostdagData, persists them, and logs a `warn!` marking the migration.
Subsequent boots validate strictly. This is a one-time self-heal on
first boot after upgrade; it is safe by construction because the
pre-existing DAG is what we treat as ground truth at the moment of
migration.

**Scope caveat (honest):** This mitigates external tampering
post-write — bit flips, adversary with disk-only access, partial
backup restore. It does **not** mitigate an active adversary with
code execution inside the process before `load_persisted_validated`
runs; such an adversary could recompute the chain from fraudulent
inputs. A fully-PQ integrity anchor (e.g. signed tip in an HSM) is
outside the scope of M-2 and not currently on the roadmap.

**Fix committed:** Sprint Y — `src/consensus/mod.rs`,
`src/storage/mod.rs`, `src/main.rs`, `tests/sprint_y_integrity_chain.rs`.
Release: v0.5.12.

### M-11 — `resolve_multiaddr` synchronous, blocks the event loop ✅ RESOLVED

**Original description:** `network/mod.rs:593-613` — DIY DNS

**Status:** Resolved in Sprint X.

### L-2 — `Transaction::merkle_root` accepts raw `[u8; 32]` ✅ RESOLVED

**Original description:** No newtype like `MerkleRoot([u8; 32])` —
accepts raw `[u8; 32]`, footgun. Block hashes, txids, address
hashes, and every other 32-byte identifier are all the same type to
the compiler; a programmer could pass one where the other is
expected and only discover the bug at runtime.

**Status:** Resolved in Sprint BB.

Introduced `core::MerkleRoot(pub [u8; 32])` as a distinct type.
`BlockHeader::merkle_root` and `Transaction::merkle_root(...)` both
now use it. The compiler refuses to interchange `MerkleRoot` with
other 32-byte hashes — the footgun is closed.

Consensus invariants preserved:

- **Wire format unchanged.** `#[serde(transparent)]` on the newtype
  guarantees bincode encodes `MerkleRoot(x)` to bytes identical to
  the bare `[u8; 32]` `x`. Every pre-L-2 block in RocksDB decodes
  correctly; every post-L-2 block encodes to the same bytes a
  pre-L-2 node would have produced. A dedicated test
  (`merkle_root_serde_is_byte_identical_to_array`) pins this.
- **PoW byte layout unchanged.** `pow_bytes` now uses
  `self.merkle_root.as_ref()` instead of `&self.merkle_root`, but
  both paths emit the same 32 bytes in the same order.
  `pow_hash_matches_hand_computed_reference` verifies the SHA-256d
  output empirically against a reference assembled with the raw
  `[u8; 32]`.

**Test coverage:** 7 new tests in `tests/sprint_bb_merkle_newtype.rs`:

- `merkle_root_serde_is_byte_identical_to_array` — the core
  serialization guarantee.
- `merkle_root_decodes_from_legacy_array_bytes` — old bytes,
  new type, clean decode.
- `block_header_round_trip_preserves_merkle_root` — full header
  round trip, highest-fidelity check.
- `pow_hash_matches_hand_computed_reference` — PoW byte layout
  unchanged.
- `merkle_root_conversions_round_trip` — `From`/`Into` soundness.
- `empty_tx_list_yields_zero_merkle_root` — `MerkleRoot::ZERO`
  matches pre-L-2 `[0u8; 32]` output.
- `single_tx_merkle_equals_that_tx_txid` — Bitcoin convention for
  single-tx blocks preserved.

### L-5 — `BLOCK_REWARD` comment overstates decay speed ✅ RESOLVED

**Original description:** Comment claimed "~5-6 years of emission". The
audit proposed "~13 years" as the replacement figure, but recomputing
`total(n) = MAX_SUPPLY · (1 − 1/2^n)` at 243 days per halving gives:
50 % at 1 halving (~0.67 years), **99 % at ~7 halvings (~4.7 years)**,
99.99 % at ~14 halvings (~9.3 years). The audit's "13 years" figure
appears to conflate halving count with years.

**Status:** Resolved in Sprint V.1.

Comment rewritten with the mathematically correct milestones
(50 % / 99 % / 99.99 %) and their half-life derivations, so the figure
cannot drift again.
