# Local restart recovery

Status: candidate implementation on `fix/persisted-restart-recovery`. This is not
an announcement that the 2026-09-14 published binary has this capability.

## Recovery modes

The node persists a disposable `state.cache` after its initial verified recovery,
then every 32 adopted canonical blocks and after a durable reorg rewrite. It
retains one previous generation. The complete `blocks.log` remains authoritative
and is still required. There is no pruning, checkpoint-import or downloaded-state
trust path. A checksum is an integrity check, not a signature or provenance proof:
only use a cache generated by your own node or a trusted backup of its data dir.

A cache contains all committed state, including the finality leak ledger, queues,
reward counters, slashing history and UTXOs. Merkle nodes and address indexes are
rebuilt from the UTXOs. A cache is accepted only when its checksum, schema,
source-tree build identity, manifest, full log-prefix digest, canonical ancestry,
head slot, admission domain and recomputed state root agree. BlockId is derived
from the log header, never deserialized from an arbitrary digest. All subsequent
blocks pass the normal consensus transition. A rejected log block aborts startup.

Writes use a temporary file, file fsync, generation rotation, atomic rename and
directory fsync. The data-directory lock covers these operations. Crash remnants
of a cache are ignored; a truncated or corrupt cache is rejected. An incomplete
last log frame is removed before appending again, while an oversized frame is a
hard error. This repair does not authorize deleting valid historical blocks.

## Upgrade and routine restart

1. Keep a healthy independent observer serving the exchange while upgrading the
   other. Never duplicate validator keys or slashing-protection data among live
   validators. Exchange read observers should be keyless.
2. On the upgraded observer, keep the existing manifest, carryover, complete data
   directory and WS checkpoint flags. The first run of this candidate must fully
   verify its historical log before it can create its first trusted local cache.
   A cache from a different source build is deliberately incompatible.
3. Wait for `state-cache: persisted`, then compare head, finalized checkpoint,
   state root and required balances with the healthy observer. Restore service
   only after catch-up and the exchange's finality/freshness policy are satisfied.
4. For subsequent supervised starts, add `--require-state-cache`. By default this
   also refuses a replay tail above 63 blocks (one lost cache generation plus the
   normal 31-block tail). Use `--max-replay-blocks N` to set an explicit budget.
5. A strict-mode refusal is an operational signal to retain the healthy standby,
   inspect the error and authorize a repair/replay window. Do not blindly restart
   in a loop, delete the log or disable the weak-subjectivity gate.

Examples (append to the existing `bloch-pos run` configuration):

```text
--require-state-cache --max-replay-blocks 63
--replay-from-genesis
```

The second option is an explicit diagnostic/recovery run, on an isolated observer.
It conflicts with `--require-state-cache`. Without strict mode, invalid/missing
caches fall back to full replay and clearly log the reason. Cache write failures
leave the block log durable but invalidate any assumed bound on replay-tail length.

A planned source upgrade currently needs one full replay on the standby. Schema
migration across builds and authenticated checkpoint state-sync are not implemented.
Weak-subjectivity verification and validator doppelganger/slashing protection
remain enabled. A WS checkpoint contains no ledger state and is not a substitute
for this local cache. Do not truncate the log at a WS checkpoint.

## Timing and capacity

Measure process-start to RPC readiness separately from readiness to credit deposits
or send withdrawals. The latter also requires catch-up, fresh peer agreement and
finality, none of which a local cache guarantees. Validator signing has its own
observation delay; RPC recovery does not bypass it.

The cache removes historical state execution for the covered prefix. It does not
make startup O(1): genesis/carryover loading, state and index reconstruction,
log scanning/hashing and canonical metadata still cost time and memory. Snapshot
writes currently run synchronously and need disk headroom for two generations
plus a temporary file. Cache files above 512 MiB are refused; defaults fall back
to replay, strict mode must fail rather than silently exceed its execution budget.
Deep reorgs outside the in-memory ring may also require historical state execution.

Qualification must use the intended Linux binary and exchange hardware, a copy of
the current complete mainnet log, a nonempty real ledger, and repeated warm/cold
restarts. Record CPU, memory peak, disk type, cache bytes, log bytes, block count,
state size, full replay time, cache load, tail replay, RPC readiness and catch-up.
Test SIGKILL during cache writes, full disks, missing/truncated/corrupt caches,
reorg replacement and both-generation failure. Compare restored state and the next
blocks to full replay. A local synthetic benchmark is not an exchange RTO SLA.

`recovery: mode=... skipped_blocks=... replayed_blocks=... elapsed_ms=...` reports
cache/replay work. It does **not** include every earlier startup step or later
network catch-up. `state-cache: persisted ... elapsed_ms=...` reports write cost.

For projections use `scripts/project-restart-recovery.py`, supplying measured or
explicitly assumed cost coefficients. It models both execution growth and the
linear log/index work retained by cached restart. Its default 2,880 daily blocks
is the 30-second slot upper bound; missed slots produce no blocks. There is no
universal prohibitive height independent of hardware, workload and the agreed RTO.
