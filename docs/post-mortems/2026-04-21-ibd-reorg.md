# Post-mortem: IBD sync + mining reorg interaction blocked multi-node operation (PR-1, PR-2)

**Date of incident:** 2026-04-21
**Duration of degraded operation:** ~2 hours from discovery to full fix deployed
**Severity in practice:** HIGH (no node could successfully join the seed once the seed had mined beyond genesis)
**Severity of impact on mainnet value:** ZERO (no funds lost, no consensus break, no chain reorganization of economically-settled state, no reward invalidation)
**Release involved:** v0.5.11 → patched on same tag with Sprints CC + DD

---

## TL;DR

Two independent bugs in the v0.5.11 codebase prevented a second node from
ever successfully syncing with the seed once the seed had mined blocks
beyond genesis. The bugs masked each other: the first prevented IBD from
being triggered at all, so the second (which only manifests once IBD runs
against a node that has also mined locally) never had a chance to surface
during audit review.

The first bug was discovered within minutes of the first Akash worker
deployment. Root-caused, fixed, tested, and redeployed inside an hour.
The fix immediately exposed the second bug, which was likewise
root-caused, fixed, tested, and redeployed inside another hour. Both
fixes were merged to `main` on the same tag (`v0.5.11`) as patch-level
additions: commits `a1af484` (Sprint CC) and `5b25f8a` (Sprint DD).

No user funds were ever at risk. The network was effectively a single
node during this window; the founder-mined blocks on the seed stayed
consistent throughout. After the fixes, every peer that joins performs a
clean IBD and enters synchronous operation as designed.

## PR-1 — Sprint CC — Stale `my_tip` announcement

### What users saw

New peers connecting to the seed would receive a `PeerTip` message
announcing `height=1` regardless of the seed's actual height. Having
observed parity with their own state, peers skipped IBD and either mined
on their own genesis chain (as the Akash worker did) or stayed idle.
The seed's block history was invisible to the network.

### Root cause

In `src/network/mod.rs`, the `NetworkNode::run` function signature took
`our_blue_score: u64, our_height: u64` by value. These were captured at
`main.rs` startup — when the DAG was freshly loaded from disk — and
baked into a `NetworkMessage::PeerTip` constant called `my_tip`. Every
new peer connection would cause `my_tip` to be re-published to the sync
topic, but `my_tip` itself never changed. Whenever the DAG accepted a
new block, `my_tip` stayed at its initial value.

The `Version` handshake message and the `heartbeat` log statement used
the same captured `our_blue_score` / `our_height` values, for the same
reason.

### Why the audit didn't catch it

The bug is invisible in single-node execution. Every existing unit and
integration test in the audit suite creates a single `GhostDAG`
instance, adds blocks to it, and asserts properties of that instance.
The `my_tip` publication path is not exercised in any unit test because
it lives inside an async `tokio::select!` loop that requires a real
libp2p swarm. There is no two-node integration harness in the existing
test infrastructure, so the "new peer connects to an advanced seed"
scenario was never simulated.

### Fix

`network::run` signature changed to accept `dag: Arc<RwLock<GhostDAG>>`
instead of the two `u64` values. A new free function
`build_current_tip(&dag, peer_id) -> NetworkMessage` reads
`tip_blue_score()` and `block_count()` under a single short read lock.
A `tokio::time::interval` called `tip_announce` publishes the current
tip every 60 seconds so that peers which connected before blocks were
accepted eventually learn the tip has advanced.

Three regression tests were added:

- `build_current_tip_reads_fresh_dag_state_each_call` — the load-bearing
  test. Builds a tip, advances the DAG via `add_block`, builds a tip
  again, asserts the second tip reflects the new state. Any regression
  that re-caches the value fails this test.
- `build_current_tip_preserves_peer_id` — guard on plumbing.
- `tip_announce_interval_is_bounded` — documents the 60s cadence is
  within sane bounds.

### Consensus impact

None. No protocol rule changed, no wire format changed, no storage
schema changed. A v0.5.11-pre-CC node interoperates with a post-CC
node at the gossipsub level; they just exchange different tip values.

### Commit

`a1af484` on `main`. Patch at `commits/a1af484`.

## PR-2 — Sprint DD — Miner loop writes no UndoData

### What users saw

Any node that (a) has mined a block locally and (b) subsequently
receives a heavier chain via IBD will fail the resulting reorg
immediately. The failure looks like
`execute_reorg: rollback failed at h=N (reorg aborted, storage in partial state): no undo data for block ..`.

In practice this meant: a freshly-deployed worker that minered one or
more blocks before its gossipsub layer connected to the seed would be
permanently unable to join the real chain, because reorg-to-real-chain
required rolling back the worker's locally-mined block(s), which had
no rollback record stored.

### Root cause

The miner loop in `src/main.rs` (the `Ok(r) if r.found` branch after
`mining::mine_block` returns a successful proof) was written before
Sprint U introduced the UndoData-backed reorg infrastructure. It
applied forward mutations inline — `put_tx_index`, `put_utxo`,
`put_coinbase_info`, `delete_utxo` — but never called
`put_undo_data`. Every other accept path (gossipsub-received blocks,
reorg re-apply) had been migrated through Sprint U and onwards to route
mutations via `reorg::apply_block_utxo_mutations`, which writes the
UndoData record as part of its contract. The miner loop was the single
straggler.

### Why the audit didn't catch it

Two reasons:

1. The bug only manifests on a node that both mines **and** is exposed
   to a reorg that crosses one of its own mined blocks. The existing
   test suite for Sprint U / U.1–U.4 exercises apply-then-rollback on
   blocks that came in through a specific code path. Locally-mined
   blocks go through a different code path, and that path had its own
   (incorrect) mutation loop. No test exercised mine-then-reorg.

2. Sprint CC (PR-1) was hiding this bug in production too. Pre-CC, the
   IBD path never actually triggered against a node that had mined.
   The two bugs masked each other: CC prevented the conditions that
   would expose DD.

### Fix

The inline mutation loop in `src/main.rs` (~20 lines) was replaced with
a single call to `reorg::apply_block_utxo_mutations(&store_m, &block)`.
Same forward mutations in the same order — the function is literally
the existing helper that every other path uses — now with the UndoData
record written as the function's documented side effect.

Two integration tests were added in `tests/sprint_dd_mined_undo.rs`:

- `mined_block_writes_undo_data_on_apply` — asserts UndoData is
  recorded after `apply_block_utxo_mutations` and has the expected
  shape (one tx_index key, one created UTXO, one coinbase txid, zero
  spent UTXOs).
- `mined_block_round_trip_rolls_back_cleanly` — the direct regression
  on the production failure mode. Applies a synthetic miner-shaped
  block, then calls `rollback_block` on it. Pre-DD this test would
  fail at the exact line that failed in production. Post-DD it
  succeeds, the coinbase UTXO is correctly removed, and the undo
  record is consumed by the rollback.

### Consensus impact

None. Same UTXO/tx_index/coinbase mutations in the same order. Same
block hash, same gossipsub wire output, same merkle root. The only
change is the addition of an UndoData record in the local `CF_UNDO`
column family, which is invisible to peers. Pre-DD nodes interoperate
with post-DD nodes at every layer of the stack.

### Commit

`5b25f8a` on `main`.

## What went well

- **Diagnostic path was clean.** Both bugs were diagnosed from log
  evidence without needing to instrument the running code. The existing
  log output at `INFO` level was informative enough to pinpoint the
  exact code paths responsible.
- **Fix discipline held.** Both fixes came with regression tests that
  specifically target the failure mode observed, not just adjacent
  properties. A future regression that re-introduces either bug will
  trip the new tests before reaching production.
- **No consensus drift.** Neither fix touched protocol rules, wire
  formats, or storage schema semantics. Mixed-version nodes running
  simultaneously on the network work fine at the gossipsub level.
- **Turnaround.** Under two hours from first symptom to fully deployed
  fix, for both bugs combined. This is the correct order of magnitude
  for post-release incident response.
- **No user impact.** The bug manifested during the earliest multi-node
  deployment. No external users held GRND during the affected window.
  No existing balances, transactions, or confirmations were affected.

## What didn't go well

- **Audit missed both.** A static code read of the audit target
  (`v0.5.10`) could not have caught either bug, because both are
  runtime interaction bugs requiring a multi-node setup to surface.
  The audit enumerated 25 findings; these are two additional findings
  that the audit format couldn't reach. Tracker entries for PR-1 and
  PR-2 are documented with equivalent rigor in
  `docs/audit/AUDIT-2026-04-20.md`.
- **No two-node integration harness existed before this incident.** The
  test suite was single-DAG or single-node throughout. The bugs would
  have been caught in a day by a simple harness that spins up two nodes
  in-process, wires their gossipsub transports together, and asserts
  state convergence. Building that harness is now a prerequisite for
  any further network-protocol change.
- **The two bugs masked each other in production, too.** Sprint CC's
  fix directly exposed the Sprint DD bug within minutes of deployment.
  In retrospect, if the worker had managed to sync at all pre-CC, the
  DD failure would have been visible earlier. Neither of these bugs is
  novel in kind — stale-cache bugs and forgotten-call bugs are among
  the most common classes in distributed systems. The lesson is about
  test coverage structure, not novel defect classes.

## Prevention

1. **Two-node test harness** — scheduled for Sprint Y or adjacent. An
   in-process two-`NetworkNode` test that:
   - Mines N blocks on node A
   - Connects B to A
   - Asserts B receives the tip announcement, triggers IBD, completes
     sync, and the two DAGs converge on `selected_tip`
   - Additionally: B mines one block locally **before** connecting to A,
     then connects. Asserts reorg succeeds without panic or state
     corruption.

  This single test would have caught both PR-1 and PR-2 in CI.

2. **Mutation-path audit.** Every `accept_block` / mining-path mutation
   loop has been cross-referenced against `apply_block_utxo_mutations`
   to confirm UndoData is captured. There is now exactly one forward
   mutation helper, used everywhere. Any future code that writes to
   UTXO/tx_index/coinbase/address-history column families must either
   route through the helper or explicitly justify bypassing it in a
   code comment reviewed as part of a PR.

3. **Post-release observability.** The Prometheus endpoint already
   exposes `groundstate_peer_count`, `groundstate_height`,
   `groundstate_tip_blue_score`. Future work: add
   `groundstate_reorg_attempts_total` / `_failures_total` counters so
   a class of failure like DD would show up on the seed's Grafana
   dashboard within seconds of first occurring in the field, rather
   than requiring log grepping.
