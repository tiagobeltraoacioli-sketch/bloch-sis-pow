# GroundState v0.5.10 — "Reorg-ready"

**Release date:** 2026-04-21
**Previous:** v0.5.9-rc1 (mainnet launch, 2026-04-20)

This is the first post-launch release. It closes every CRITICAL
finding from the launch-day audit (see
`docs/audit/AUDIT-2026-04-20.md`) and lands the full UTXO reorg
handling path that mainnet shipped without.

---

## Highlights

### Full UTXO reorg handling (closes audit finding C-1)

Before this release, `accept_block` was forward-only. A competing
fork with higher blue work would leave the UTXO set inconsistent
with the selected chain — the node would *think* it was on the
heaviest chain but spend from a different one. On a young network
like GroundState at mainnet launch this is a latent consensus-split
bug.

v0.5.10 ships a complete reorg path, built across four sub-sprints:

- **Per-block undo data.** Every accepted block writes an
  `UndoData` record to a new `CF_UNDO` column family, capturing
  the full mutation set (created UTXOs, spent UTXOs with their
  pre-spend output, tx-index entries, coinbase info). Undo data
  lets any block be rolled back byte-identically to its pre-accept
  state.
- **`rollback_block` primitive.** Consumes an `UndoData` record
  and replays it in reverse. Byte-identical round-trip is verified
  by the U.2 test
  `apply_rollback_apply_rollback_is_stable`.
- **`reorg::compute_reorg_plan` / `reorg::execute_reorg`.** Given
  old-tip and new-tip block hashes, these functions find the LCA,
  produce a rollback + apply plan, and execute it atomically with
  respect to storage state. Mempool transactions from rolled-back
  blocks are re-validated against the new UTXO set and reinjected
  if still spendable.
- **4-way disposition dispatcher in `accept_block`.** Classifies
  each incoming block as **Extension**, **ForkLoser**, **Reorg**,
  or **Unexpected**, and routes through the correct primitive.
  Fork-losers are now persisted to `CF_BLOCKS` so a future reorg
  can bring them in without re-downloading.

**Tests:** 52 new tests across U.1 / U.2 / U.3 / U.4 pin this
subsystem. The U.4 harness includes a flip-flop
`A(2) → B(3) → A(5)` double reorg that would catch any UTXO
leakage between chains.

### Deterministic ML-DSA-65 keygen from seed (closes audit finding C-2)

Wallet recovery from a BIP39 seed phrase now produces the same
signing key across devices and across platforms. Previously the
upstream `pqcrypto-internals` crate offered no seeded keygen
entry point, so a GroundState seed phrase could only recover a
wallet on the original machine.

To fix this without forking the upstream cryptography:

- Anthropic's `Groundstate100/pqcrypto-fork` is a strict superset
  of upstream `rustpq/pqcrypto` v0.2.11. It adds a
  `with_seeded_rng(&[u8; 32]) -> SeededRngGuard` RAII API.
- `crypto::generate_keypair_from_seed(seed)` uses the guard to
  produce deterministic output.
- After the guard drops, the internal RNG reverts to the OS CSPRNG
  — no leakage into other keygen callers.

**Tests:** 5 tests in `tests/sprint_t1_seed_determinism.rs`.

### Duplicate-tx rejection via structural merkle check (closes audit finding C-3)

`validate_tx_in_block_with_maturity` now builds a `HashSet` of
`(prev_txid, prev_index)` pairs for the block being validated and
rejects the block on collision. Previously two txs in the same
block could both "spend" the same UTXO because neither had
committed to storage at validation time.

### Wallet hygiene (closes M-4, M-5, M-6, L-4)

- **Argon2id upgraded** to m_cost=262144, t_cost=4, p_cost=4
  (OWASP 2024 interactive-auth guidance).
- **Password policy:** minimum 12 characters plus an 18-entry
  denylist of common / leaked passwords.
- **Secure RNG:** every keygen and nonce site now uses
  `rand::rng()` (OS-backed), not `rand::thread_rng`.
- **Atomic wallet writes:** new `util::atomic_write` helper writes
  to a tempfile and renames, guaranteeing no torn wallet files.

### Other audit quick wins (Sprint S)

- Repository URL corrected to `Groundstate100/groundstate` (M-1).
- `CHECKPOINT_DEPTH = 1000` / `PRUNING_DEPTH = 10000` constants
  introduced and enforced at `accept_block` entry, preventing
  deep reorgs from threatening finality (H-6).
- Crypto size constants (`PUBKEY_SIZE=1952`, `PRIVKEY_SIZE=4032`,
  `SIG_SIZE=3309`) pinned against ML-DSA-65 by integration tests
  (H-2).

## Upgrade notes

### No consensus break

v0.5.10 does not change any rule that affects block validity. A
v0.5.9-rc1 node and a v0.5.10 node will both accept the same
blocks. The difference is that v0.5.9-rc1 could silently diverge
on a reorg, and v0.5.10 cannot.

### Undo-data backfill

v0.5.9-rc1 did not write `UndoData` records, so blocks already on
disk when a node upgrades to v0.5.10 will not have undo data. In
practice this means:

- A reorg that would need to roll back a pre-v0.5.10 block will
  fail gracefully (logged, accepted block is persisted in
  `CF_BLOCKS` and the DAG, but the UTXO rollback cannot execute).
- The `finalized_height` + `CHECKPOINT_DEPTH` boundary means any
  block deeper than 1000 blocks is un-reorganizable anyway, so
  the missing-undo window only matters for blocks within the
  finality window at upgrade time — a few hours of operation.

No action required from node operators. Mining nodes should
upgrade in their own time.

### Wallet file format

Wallet files written with v0.5.10 use Argon2id with m_cost=262144.
Decrypting these on older (v0.5.9-rc1) binaries will work only if
the older binary also supports this parameter set — check before
downgrading. All wallet files written before v0.5.10 remain
decryptable on v0.5.10.

### Password re-prompt on weak credentials

Users with a pre-v0.5.10 password under 12 characters will not be
able to re-encrypt their wallet with v0.5.10 without choosing a
new password. Decryption of existing wallets is not affected.
