# GroundState v0.5.11 — "Audit fortnight"

**Release date:** 2026-04-21
**Previous:** v0.5.10 (reorg-ready, 2026-04-21)

v0.5.11 bundles four sprints of audit remediation that landed on top
of v0.5.10 over the following day. The headline is a sharp jump in
the audit scoreboard: **40 % of findings resolved in v0.5.10 → 88 %
in v0.5.11**, with **every CRITICAL, HIGH, and LOW finding now
closed**.

Three remediations made it into the core path (reorg handling, seed
determinism, duplicate-tx rejection) in v0.5.10. What remained was
everything else — 15 findings across HIGH / MEDIUM / LOW. v0.5.11
closes 12 of those 15 in a tight cycle.

---

## Highlights by audit severity

### HIGH — 3 of 6 → 6 of 6 ✅

**H-1 (genesis coinbase message)** — the genesis block's
`script_sig` carries the legacy string `"14010101 GRND"` from an
abandoned tokenomics draft, and because genesis is immutable the
string cannot be edited. `README.md` now has a dedicated "Genesis
coinbase message" section under Security that (a) acknowledges the
legacy text, (b) confirms that `MAX_SUPPLY = 21,000,000 GRND` is
the authoritative constant enforced by consensus, and (c) explains
why the message cannot be changed. Block explorers and external
auditors parsing `script_sig` now have a canonical reconciliation
to reference.

**H-3 (Ed25519 peer identity in an otherwise PQ transport)** — the
libp2p peer identity that signs the Kyber handshake transcript is
classical Ed25519. Previous marketing said "hybrid post-quantum
transport" without distinguishing the post-quantum KEM from the
classical signature. `README.md`, `docs/index.html`, and the
handshake PDF source now carry a per-primitive breakdown — KEM is
PQ, session cipher is classical-symmetric, peer identity is
classical Ed25519 — plus a spelled-out threat model
("harvest-now-decrypt-later is defeated; active MITM by a future
quantum adversary is not"). A fully-PQ identity path would require
forking libp2p and remains off the roadmap for this release.

**H-4 (PDF claim "AES-256-GCM" but code uses ChaCha20-Poly1305)** —
the handshake PDF documented `AES-256-GCM with random 96-bit
nonce`, but the actual transport code uses `ChaCha20-Poly1305` with
a counter-derived nonce. Both are secure AEADs, and the counter
construction is in fact strictly stronger than random-nonce
AES-GCM (no birthday-bound collision risk until 2^64 messages vs
~2^48), but the public claim was factually wrong. The PDF source
(`FIRST_POST_QUANTUM_HANDSHAKE.md`), `README.md`, and
`docs/index.html` now all say `ChaCha20-Poly1305 (RFC 7539)` for the
session cipher. AES-256-GCM is retained (correctly) for the wallet
keystore on disk. **Operators should re-export the PDF from the
markdown source and replace the public artifact.**

**H-5 (`past_blue_set` bound under-counted anticone)** — the walk
was bounded at `2 * K = 20` selected-chain hops with K=10, which
could under-count the anticone and classify a red block as blue
whenever the DAG had branches beyond that window — a silent
consensus split at high latency. Raised to `K * 100 = 1000` hops
and added a `warn!` log when the bound is hit, so drift becomes
observable in production before it matters. Long-term fix
(Kaspa-style reachability tree, O(1) ancestor queries) remains on
the roadmap.

### MEDIUM — 4 of 11 → 8 of 11

**M-3 (`MAX_REACHABILITY_DEPTH` silent cutoff)** — `is_ancestor`
silently clamps its BFS bound, so a true ancestor beyond 1024
hops returns `false`. Added a `warn!` log at the clamp site with
both block hashes, so the anomaly surfaces in logs.

**M-9 (`assert!` in `add_block` panicked the node)** — previously,
an invalid block slipping past upstream validation could hit
`assert!(!parents.is_empty())` or `assert!(!has(hash))` and panic
the entire process. Now returns `Result<GhostdagData,
ConsensusError>` with `NoParents` and `DuplicateBlock` variants;
callers reject the block cleanly without tearing the node down.
All 17 callsites updated. Three new regression tests pin the new
behavior.

**M-10 (`DefaultHasher` for gossipsub MessageId)** —
`std::hash::DefaultHasher` is not stable across Rust versions, so
nodes on different toolchains could compute different IDs for the
same payload and break gossipsub dedup. Replaced with SHA-256
truncated to 16 bytes. Deterministic across toolchains, collision-
resistant within realistic network sizes, microseconds per message.

**M-11 (`resolve_multiaddr` blocked the event loop)** —
`resolve_multiaddr` was synchronous, calling
`std::net::ToSocketAddrs::to_socket_addrs()` inside the libp2p
swarm loop. A slow DNS seed stalled the entire loop — gossipsub
propagation, connection events, other dials — for the full
resolver timeout. Now `async fn` using
`tokio::net::lookup_host`. Three callers updated with `.await`;
all were already in async contexts. Four regression tests,
including a compile-time guard against regressing back to sync.

### LOW — 1 of 5 → 5 of 5 ✅

**L-1 (`crypto::verify()` silent on parse failure)** — behavior
was correct (return `false`, required by consensus) but a parse
failure was indistinguishable from a semantic verify failure.
Added `debug!` logging at both parse-failure sites; consensus
behavior is unchanged.

**L-3 (`resolve_multiaddr` silent fallback)** — DNS errors and
no-IPv4-records cases now `warn!` with the host and error reason.
Previously fell back to the raw multiaddr with no indication why
the subsequent dial failed.

**L-5 (`BLOCK_REWARD` comment overstated decay speed)** — the
comment said "~5-6 years full emission", which conflated several
metrics. The audit draft suggested "~13 years to 99 %", which was
also wrong (confused halving count with years). Recomputing
`total(n) = MAX_SUPPLY · (1 − 1/2^n)` at 243 days per halving
gives: **50 % at 1 halving (~0.67 y), 99 % at ~7 halvings (~4.7
y), 99.99 % at ~14 halvings (~9.3 y)**. Comment rewritten with
the accurate milestones; two regression tests in
`tests/sprint_v1_quickwins.rs` pin the formula.

**L-2 (no `MerkleRoot` newtype)** — `BlockHeader::merkle_root`
was a bare `[u8; 32]`, indistinguishable from block hashes, txids,
and every other 32-byte identifier. A programmer could pass one
where another was expected and only discover the bug at runtime.
Introduced `core::MerkleRoot(pub [u8; 32])` with
`#[serde(transparent)]` so the wire format is byte-identical to
`[u8; 32]` — every pre-L-2 block in RocksDB decodes cleanly and
every PoW hash is preserved bit-for-bit. Seven new tests pin the
consensus-invariance guarantees. **The compiler now refuses to
interchange `MerkleRoot` with other 32-byte hashes.**

## Upgrade notes

### No consensus break

v0.5.11 does not change any rule that affects block validity.
Every mainnet block accepted by v0.5.10 is accepted identically by
v0.5.11. The `MerkleRoot` newtype in particular is wire-identical
to `[u8; 32]` — RocksDB state written by v0.5.10 loads unchanged on
v0.5.11, and pre-v0.5.11 pow hashes are bit-identical to post-
v0.5.11 pow hashes of the same header bytes.

### `add_block` API change (internal)

The in-crate `GhostDAG::add_block` method now returns
`Result<GhostdagData, ConsensusError>` instead of panicking on
malformed input. External consumers of the crate need to add
`.map_err(...)?` or `.expect(...)` at each callsite. Inside the
main binary this was handled in the same patch.

### Node operators

- Log output has new `warn!` and `debug!` lines from the L-1 / L-3
  / M-3 / H-5 fixes. None are fatal; they surface conditions that
  were previously silent. Dashboards tuned to the v0.5.10 log
  vocabulary should add these message patterns.
- Nothing else requires action. Rebuild and restart.

### Public-facing PDF

The handshake PDF at groundstate.network still reflects the old
AES-256-GCM / implicit-all-PQ claims. **Re-export
`FIRST_POST_QUANTUM_HANDSHAKE.md` to PDF and replace the public
artifact.** The markdown source in the repository is already
corrected.
