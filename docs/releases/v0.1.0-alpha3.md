# Bloch-SIS-PoW — v0.1.0-alpha3

Two **consensus** fixes for bugs the `alpha2` k-ramp exposed once block
production un-choked. **Unaudited research chain; the coin (BLCH) has no value.**
Bloch is **ownerless** — a *candidate* release node operators adopt or not.

## Why this release

`alpha2` relaxed the residual gate back to k=4, so blocks stopped being choked —
and that surfaced two latent consensus bugs that had been masked while the chain
crawled. Non-mining nodes stopped converging (they froze on ingest) and the sole
miner ran away at ~7 blocks/s. Both are fixed here; both required a coordinated
restart from a shared base.

## Consensus — finality checkpoint unit fix (nodes froze on ingest)

The finality checkpoint was **computed in blue-score units but enforced in height
units**. `accept_block` wrote `finalized_height = tip_blue_score − CHECKPOINT_DEPTH`,
then rejected any block with `block.height <= finalized_height`. Because blue-score
runs ahead of height by the DAG width, once that skew passed `CHECKPOINT_DEPTH`
(1000) a node "finalized" a height **above its own selected tip** and permanently
rejected every chain-extending block — it received gossip tips but never advanced.
The sole miner escaped only because the miner path bypasses `accept_block`, so it
climbed alone while every ingesting node froze.

- The checkpoint (and the pruning depth, same variable) is now the **selected
  tip's height**, not `tip_blue_score()`.
- A **one-time startup clamp** heals the already-poisoned `finalized_height`
  (the monotonic guard in `accept_block` cannot lower it), clamping it down to a
  height-based ceiling on boot.

## Consensus — ASERT difficulty re-anchor (block production ran away)

ASERT clamped the **absolute** genesis-anchored schedule exponent to ±4× — a
**lifetime** cap, not a per-step limiter — so difficulty could never exceed 4×
`GENESIS_BITS` however much hashrate joined. With the k throughput filter relaxed,
that let the miner flood and could never rise to meet real hashrate (ASICs/FPGA).
This cannot self-correct, so it is fixed by a **height-switched re-anchor**:

- At `ASERT_ANCHOR2_HEIGHT` the schedule re-anchors to a fresh
  `(height, timestamp, bits)` reference, resetting the ~62-day accumulated
  schedule debt and returning blocks toward the ~30 s target.
- **Only** the re-anchored regime (`anchor_height > 0`) gets a **wide** clamp, so
  difficulty can track hashrate freely from here. Blocks below the anchor keep the
  genesis anchor and the ±4× bound **byte-for-byte**, so every historical
  `expected_bits` still validates on resync (VULN-01 intact) — **no fork**.
- `ASERT_ANCHOR2_BITS` is calibrated to the observed miner rate (~30 s); ASERT
  converges any residual error with the 2-day half-life. It is a **calibration
  knob**, not a hardness claim.

## Rollout — coordinated reset from a shared base

`ASERT_ANCHOR2_HEIGHT` is the shared snapshot-tip **height** (392_303) + 1 — note
that 393_386 was that tip's *blue-score*, the very unit confusion fixed above.
Because the reset is coordinated (every node wiped to the same base, every node on
this build, started together), no node holds a post-anchor block under the old
rules, so there is no fork surface. Re-pin `ASERT_ANCHOR2_HEIGHT` /
`ASERT_ANCHOR2_TIMESTAMP` / `ASERT_ANCHOR2_BITS` against the real base at rollout.
