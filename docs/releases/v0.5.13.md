# v0.5.13 — Pre-IBD mining bug fix (Sprint GG)

**Release date:** 2026-04-22
**Type:** Bug fix — critical for new miners
**Breaking changes:** none (wire, storage, and consensus unchanged)

## Context

New miners joining mainnet on 2026-04-21 and 2026-04-22 reported
that their mining efforts were not producing credited blocks despite
CPU consumption. Investigation on 2026-04-22 02:00 UTC identified
the root cause: the miner loop started hashing against the local
DAG tip immediately, **without waiting for Initial Block Download
(IBD) to complete**.

A node joining a running mainnet would:
1. Begin IBD — requesting headers and blocks from peers
2. **Simultaneously** launch the miner loop against the local tip
   (genesis or whatever low height it had reached)
3. Produce blocks at height 1, 2, 3… (whatever the partial tip was)
4. Have those blocks rejected by the network with `REJECTED:
   finality: block at or below finalized height`
5. Never receive rewards, because finality rejects the orphan blocks

Visible symptoms in mainnet seed logs around this period:

- `← block h=29` / `← block h=42` / `← block h=47` from fresh peers
- Seed's `block_count` frozen (no new accepted blocks from the work
  being expended network-wide)
- Peer count growing (45+) with no corresponding chain advance

## Fix

`src/main.rs` miner loop now checks `node_state.is_syncing` at the
start of every iteration. When true, the miner sleeps 5 seconds and
skips the round. When IBD completes (`is_syncing` flips false), the
miner resumes naturally on the next tick.

Operator-visible logs during the transition:

- `⛏ IBD in progress — miner paused, will resume when sync completes`
  (once, when syncing becomes true)
- `⛏ IBD complete — miner resumed at tip` (once, when cleared)

No log spam on every 5s sleep — only transitions are logged.

## What was not the bug

Early triage suggested the finality-rejection rate was high
(hundreds of rejections). Recounting confirmed **one** finality
rejection in the trailing 2 hours on the seed. The real symptom is
more subtle — most rejected blocks from pre-IBD miners never reach
the seed at all, because gossipsub mesh fragmentation drops them
before they're broadcast. What shows up as REJECTED in seed logs is
only the tip of the iceberg; the bulk is invisible.

The fix addresses the producer side: miners no longer generate these
doomed blocks in the first place. This is better than trying to
accept them, which would break finality guarantees.

## Testing

- `tests/sprint_gg_pre_ibd_mining.rs` — 4 regression tests verifying
  the `is_syncing` primitive and the branch condition.
- Full test suite: 179 tests passing.

A true end-to-end test (two-node network, fresh miner joining, observe
no pre-IBD block submissions) is blocked on the two-node test harness
(Sprint EE on the roadmap). This release ships with unit-test coverage
of the fix primitive and relies on mainnet observation for full
validation.

## Upgrade

Mainnet operators running v0.5.12 should upgrade to v0.5.13:

```bash
docker pull groundstate77/groundstate:v0.5.13
docker stop grnd-seed && docker rm grnd-seed
docker run -d --name grnd-seed --restart unless-stopped \
  -p 0.0.0.0:16110:16110 -p 0.0.0.0:16111:16111 \
  -p 127.0.0.1:16210:16210 -p 0.0.0.0:16310:16310 \
  -v grnd-data:/grnd-data -e RUST_LOG=info \
  groundstate77/groundstate:v0.5.13 \
  --rpc-bind 0.0.0.0 --rpc-port 16210 \
  --listen /ip4/0.0.0.0/tcp/16110 --data-dir /grnd-data \
  --metrics --metrics-addr 0.0.0.0 --metrics-port 16310
```

Miners running earlier versions should especially upgrade — they
are the ones affected. Chain state is preserved on the volume.

## Credits

Diagnosis driven by operator reports that mining was not producing
credited blocks despite activity. The log trail that enabled this
fix came from `getsupplydistribution` — only 3 distinct addresses
funded after 2675 blocks, with just one external miner earning
~98 GRND. The asymmetry was the signal that something was wrong
with how new miners joined the network.
