# v0.5.12 — Integrity chain (M-2)

Released: 2026-04-21

## Summary

Sprint Y closes audit finding M-2: the persisted GhostDAG data was
trusted verbatim on node startup, leaving a class of attacks where
an adversary with disk-level access could edit `blue_score`,
`mergeset_blues`, or `selected_parent` and force the node to resume
with a fraudulent consensus view.

A hash-chain over `GhostdagData` is now written alongside CF_DAG in
a new column family, `CF_DAG_INTEGRITY`. Each block's integrity
record covers its own canonical bytes plus the parent's integrity
hash, so tampering with any ancestor breaks validation for every
descendant. The validator runs in `O(n)` time over the DAG and is
invisible in the block-accept hot path (integrity is written
atomically with GhostdagData via a WriteBatch).

This is a defense-in-depth release. No user-facing behavior
changes; no wire-protocol or block-content changes. The new
defensive surface activates only on node startup.

## Upgrading

First boot after upgrade will self-heal: the validator detects the
empty `CF_DAG_INTEGRITY`, computes fresh integrity records from
the existing DAG (treating the current state as ground truth), and
persists them. A `warn!` log entry marks this:

```
CF_DAG_INTEGRITY was empty — self-healed N integrity records.
This is expected on first boot after Sprint Y upgrade.
Subsequent boots will validate strictly.
```

Subsequent boots validate against the persisted chain. If any
integrity record is missing in isolation (partial coverage), or if
any stored integrity hash disagrees with the recomputed value, the
node logs the offending block and exits with status 1. This is
intentionally fatal — the operator must investigate disk integrity
or provenance of the data directory before the node can rejoin.

No manual migration is required. No configuration flags changed.

## Threat model

What M-2 mitigates:

- **Silent disk corruption** (bit flip, bad sector, bad cable).
  RocksDB doesn't checksum per-value by default; a corrupted
  `GhostdagData` entry is returned as if valid. The integrity
  chain catches this on next boot.
- **Disk-only adversary.** An attacker with read/write access to
  the data directory but no code execution inside the node process
  (stolen backup, shared-host filesystem access, post-compromise
  disk cloning).
- **Partial backup restore.** If the operator restores CF_DAG
  from one snapshot and CF_DAG_INTEGRITY from another (or none),
  the mismatch is visible.

What M-2 does not mitigate:

- **Active adversary with code execution inside the process.**
  Such an attacker can recompute the chain from fraudulent inputs
  and sign their own integrity records. The only defense is to
  prevent code execution in the first place, and/or anchor the tip
  in an out-of-process trust root (HSM, external checkpoint).
  Out of scope for M-2.
- **Gossipsub-delivered fraudulent blocks.** Blocks received from
  peers still go through `add_block` validation (PoW, merkle,
  signatures, UTXO). The integrity chain is about *persisted*
  state, not wire-delivered state.
- **Consensus correctness beyond stored fields.** If the stored
  `GhostdagData` is consistent with its own integrity but was
  wrong when originally computed (e.g. a bug in
  `classify_mergeset`), the chain validates it. M-2 catches
  tampering, not incorrect-but-untampered data. A full PHANTOM
  re-validation on load is a stricter but much slower alternative
  we did not take; re-validation for a mainnet-sized DAG is
  minutes of startup.

## Consensus-preservation

Zero wire-protocol changes. Zero block-content changes. Nodes
running v0.5.11 interoperate with v0.5.12 nodes over gossipsub at
every layer: same block hashes, same merkle roots, same signature
formats. The integrity chain is strictly local-storage metadata.
A v0.5.12 node can run against a database populated by a v0.5.11
node (and will self-heal once, then validate strictly thereafter).
A v0.5.11 node reading a v0.5.12 database ignores `CF_DAG_INTEGRITY`
and behaves exactly as before.
