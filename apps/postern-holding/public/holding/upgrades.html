Node release and network upgrades — technical specification.

What has shipped, what remains in testing and the parameters of each feature. Signed node release 1708953d includes validator hardening and the finality-certificate RPC. It schedules no new hard fork: all new HF1/HF2/HF3 activation gates remain disabled.

Current node release.

RELEASED1708953d / signed Linux x86-64 / 21 October 2026

The Genesis-4 upgrade includes durable signing-history protection, host-level signer locking and a strict signer anchor, duplicate-validator detection, improved attestation retries, stricter node-local ML-DSA relay verification and the finality-certificate RPC.

All 61 managed fleet validators were upgraded and verified on 22 October 2026. Frozen-set finality, own-target votes, canonical-signature activation, the ML-DSA consensus pin, growth cap, the new post-quantum suite and KES remain disabled. Existing mainnet activation epochs are unchanged.

1. Signature suites.

STATUSImplemented — in testing; activation disabled

Bloch authorizes spending with hybrid post-quantum signatures: two independent schemes combined with AND, so a signature is valid only if both parts verify. Suite 0x0001 stays the default and does not change. The upgrade adds an optional suite 0x0003 that pairs a stateless hash-based scheme with Falcon-1024.

Suite 0x0003 uses the SHA-3/SHAKE hash family, consistent with Bloch’s SHA3-256 hashing.

Rules

  • AND combination. Both signatures in a suite must verify; an attacker must break both schemes.
  • Addresses commit to their suite. An address is the SHA3-256 hash of the suite-tagged public key, which prevents downgrade and cross-suite key reuse.
  • Verification cost is charged per suite. A 0x0003 signature is priced from its measured verification time; a typical 0x0003 transfer costs about 6× today’s fee.
  • Nothing to do for suite 0x0001 users. Existing keys and addresses keep working unchanged.

Implementation notes

  • ML-DSA verification is deterministic and platform-independent: one portable implementation runs on every CPU.
  • Canonical signature encoding is enforced, and the suite identifier is bound into the signed context.
  • The SLH-DSA implementation passes the NIST ACVP test vectors.
  • An independent external audit is planned before activation.

2. Finality under partitions.

STATUSImplemented — in testing; activation disabled

The proposed upgrade counts finality over a frozen validator set C instead of the live active set. The set changes only through a finalized checkpoint, so both sides of a network partition measure their votes against the same total — and two disjoint sides can never both reach the quorum.

Finality rule parameters
ParameterValue
Quorum3·w ≥ 2·total, where w is the weight of included votes and total is the weight of C
Validator set CFrozen; changes only through a finalized checkpoint
Leaving CNo included vote for 90 epochs (24 h)
Rejoining CAutomatic when the validator votes again
Inactivity leakStill reduces rewards and balances; does not change the finality denominator
Vote eligibilityA vote counts only when its source and target are checkpoints of the voter’s own chain; foreign votes count as absent

Activation remains subject to further qualification. This mechanism remains disabled in release 1708953d.

The intended quorum property

Each side needs at least two thirds of the weight of the same frozen set C. Two disjoint groups of validators cannot each hold two thirds of one total, so conflicting checkpoints cannot both reach the quorum.

3. Finality certificates.

STATUSReleased — node 1708953d

A finality certificate carries proof data for independent verification of a checkpoint. Verification starts from a trusted earlier finalized checkpoint and checks signed votes, validator-set proofs and ancestry; it does not remove that trust-anchor requirement.

4. Validator signer protection.

STATUSReleased — node 1708953d

With a persistent strict signer anchor configured, the validator keeps signing history outside its data directory and checks for local duplicate signers or restored stale data. Network observation also detects unexpected signatures from the same validator identity.

  • Record before release. The signing record is persisted before any signature is released.
  • Per-key lock. A host-level lock per key, held outside the data directory: a second local signer using that anchor refuses to start.
  • Rollback detection. The strict signer anchor detects data-directory signing records that fall behind the preserved anchor. Preserve both during recovery.
  • Host migration. Preserve identity, signing records and the signer anchor; retire the old signer before moving to a new host. Follow the published operator guide.

5. Key-evolving signatures (KES).

STATUSImplemented — in testing; activation disabled

Each validator signs with a key-evolving signature key. The key moves forward one period at a time and the keys of past periods are erased, so a key compromised today cannot sign for earlier periods (forward security).
